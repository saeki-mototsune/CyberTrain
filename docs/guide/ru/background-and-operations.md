# Фоновая работа и эксплуатация

## Фоновая работа

Приложение, которому нужно сделать что-то вне запроса (отправить уведомление
после того, как ответ ушёл, каждую ночь вычищать старые строки, повторить
неудавшийся вызов), поручает это фреймворку, а тот выполняет работу в фоновых
потоках обслуживающего процесса или отдельного процесса-обработчика. Задача —
это класс в `app/jobs/`, как в Rails. Задачам и задачам по расписанию нужна
строка `require "cybertrain/jobs"` в `bin/<app>.rb` и `bin/db.rb`; её
добавляет `cybertrain generate job` ([Подсистемы](how-it-works.md#subsystems)):

```ruby
# app/jobs/welcome_job.rb
class WelcomeJob < Cybertrain::Job::Base
  retry_on Cybertrain::Mailer::TimeoutError, wait: 60, attempts: 5
  discard_on ArgumentError

  def perform(args)
    user = User.find(Cybertrain::Cast.int(args["user_id"]))
    Cybertrain::Mailer.deliver(to: user.email, subject: "Welcome", body: "Hello!\n")
  end
end
```

```ruby
# в действии, после сохранения пользователя
WelcomeJob.perform_later("user_id" => @user.id)
WelcomeJob.perform_in(600, "user_id" => @user.id)   # или perform_at(time, args)
```

```ruby
# config/app.rb (или файл, который bin/<app>.rb подключает до Cybertrain::Main.run)
Cybertrain::Scheduler.cron("0 4 * * *", "nightly digest", job: "DigestJob")
Cybertrain::Scheduler.every(300, "refresh rates") { Rates.refresh }
```

- **Где это выполняется.** Задачи выполняются в `job_threads` потоках задач
  (3, `CYBERTRAIN_JOB_THREADS`); задачи по расписанию — в собственном потоке
  планировщика, так что долгая задача никогда не задерживает задачу по
  расписанию. И те, и другие запускаются, когда бинарный файл обслуживает
  запросы (`./<app>`, `./<app> server`) или работает как обработчик
  (`./<app> worker`, см. [Роли процессов](#process-roles)), после того как
  при запуске подключена база данных и задан `SPINEL_WORKERS`; команды
  `migrate`, `db ...`, `jobs ...`, `console` и `Main.command` никогда их не
  запускают, как и `Cybertrain::Test::Client`. Если задачи подключены, их
  потоки запускаются в каждом таком процессе, даже в приложении без единого
  класса задачи:
  фреймворк регистрирует собственную задачу отправки почты
  (`Mailer.deliver_later`,
  [Отправка электронной почты](external-services.md#sending-e-mail)).
- **Таблица.** Задачи — это строки `cybertrain_jobs`, таблицы, которую
  фреймворк создаёт сам (`CREATE TABLE IF NOT EXISTS`, при первом
  использовании) и не включает в `db/schema.rb`. Внутри `DB.transaction`
  строка фиксируется или откатывается вместе с остальным. Каждый поток задач
  забирает самую старую наступившую строку в короткой транзакции
  `BEGIN IMMEDIATE`, выполняет её вне транзакции и ищет следующую; когда
  ничего не наступило, он ждёт `job_poll_interval` секунд (1), так что
  задача, поставленная запросом, начинается примерно через секунду. Строка
  находится в состоянии `queued`, `running`, `done`, `failed` (повторы
  исчерпаны; она остаётся, чтобы вы её изучили) или `discarded` (её
  остановил `discard_on`).

### Классы задач

`spin run gen` читает каждый файл в `app/jobs/` (и во вложенных каталогах:
`Admin::ReportJob` в `app/jobs/admin/report_job.rb`) и записывает в
`gen/jobs.rb` вторую половину каждого класса, среди предков которого есть
`Cybertrain::Job::Base`: `perform_later`, `perform_at`, `perform_in`,
`perform_now`, `job_kind` и код, который её выполняет, — и регистрирует
класс. `cybertrain generate job send_digest --retry
Cybertrain::Mailer::TimeoutError:60:5` пишет файл класса и тест к нему.

- **`args`** — это Hash, переданный в `perform_later`, сохранённый как JSON
  и прочитанный обратно как `Hash<String, Object>`: сужайте его значения
  через `Cybertrain::Cast.int(args["user_id"])`, `Cast.str`, `Cast.hash`,
  `Cast.array`. Задача принимает только этот один Hash; передавайте id, а не
  записи (так советует и Rails). `perform_later` возбуждает `ArgumentError`
  для всего, что не Hash, а без аргумента отправляет `{}`.
- **Постановка в очередь.** `perform_later(args)`, `perform_at(time, args)`
  и `perform_in(seconds, args)` возвращают id строки; вид строки — имя класса
  (`"WelcomeJob"`, `"Admin::ReportJob"`). `perform_now(args)` выполняет
  `perform` в вызывающем потоке, без очереди, без политики повторов и без
  rescue, и возвращает `nil`: как раз то, что нужно тесту.
- **Тело класса.** Каждый класс задачи определяет `perform(args)`
  (генератор отвергает класс, который его не определяет и не наследует).
  `retry_on`, `discard_on` и `limits_concurrency` читаются как текст, по
  одному на строку, с литеральными значениями (Integer или
  `:polynomially_longer` для `wait:`, Integer для `attempts:` и `to:`,
  String в кавычках для `key:`); блок, лямбда, `5.minutes`, запись через
  `=>` или комментарий в конце строки останавливают `spin run gen` с
  указанием файла, строки и того, что написать вместо этого.
- **Какие классы исключений.** `retry_on` или `discard_on` называет класс,
  который программа определяет до задачи: класс ядра (`ArgumentError`,
  `KeyError`, ...), один из классов `...Error` фреймворка (нужный require
  генератор добавляет сам) или класс приложения, определённый в
  `app/models/`, в `app/jobs/application_job.rb` или выше этой строки в
  файле самой задачи. Всё остальное останавливает `spin run gen`: под Spinel
  `rescue`, называющий класс, которого программа не определяет, может
  проглотить любое исключение (spikes/NOTES.md, правило 89).
- **`ApplicationJob`.** Класс `ApplicationJob < Cybertrain::Job::Base` в
  `app/jobs/application_job.rb` сам задачей не является: его строки
  `retry_on` и `discard_on` применяются к каждой унаследованной от него
  задаче после её собственных, а его `limits_concurrency` — к задаче, которая
  своего не объявляет. Любой другой класс задачи может быть родителем; тогда
  он сам по себе тоже задача.
- **`Job.handle`, короткая форма.** Блоку, зарегистрированному под видом-String,
  не нужны ни класс, ни генератор; он получает полезную нагрузку String и
  политику по умолчанию, описанную ниже:

  ```ruby
  # config/app.rb
  Cybertrain::Job.handle("notify", concurrency: 1) { |payload| Notifier.post(payload) }

  # где угодно, позже
  Cybertrain::Job.enqueue("notify", JSON.generate({ "text" => "Deployed" }), run_at: Time.now + 60)
  ```

  Классы задач и виды `Job.handle` делят одно пространство имён, так что
  `Job.enqueue("WelcomeJob", json)` добавляет ту же строку, что и
  `perform_later`. `Job.enqueue` отвергает незарегистрированный вид.

### Повторы и отбрасывание

- **Политика по умолчанию.** Исключение, которому не соответствует ни одна
  строка класса (и любое исключение блока `Job.handle`), повторяется через 1,
  5, 15, а затем через 60 минут, с `Class: message` (до 1000 символов) в
  `last_error`, пока не будут исчерпаны `job_max_attempts` (5) попыток;
  тогда строка становится `failed`. `NotImplementedError` (ещё не написанный
  хелпер), `SystemStackError` или другой `ScriptError` из кода задачи
  следуют этой же политике, хотя ни один из них не `StandardError`; любое
  другое исключение вне `StandardError` пишется в лог (`[ERROR] Job thread
  N: ...`), поток задач продолжает работу, а строка остаётся `running`, пока
  её не заберёт восстановление (ниже).
- **`retry_on Klass, wait: 60, attempts: 5`.** `wait:` — это секунды (3,
  если не указано, — умолчание Rails) или `:polynomially_longer`
  (`attempts ** 4 + 2` секунды: 3, 18, 83, 258, ...); `attempts:` (5, если
  не указано) считает каждую попытку, включая первую. Строк может быть
  несколько: побеждает первая, чей класс соответствует исключению (подкласс
  тоже соответствует), поэтому пишите более узкий класс первым.
  `retry_on StandardError` перед `discard_on ArgumentError` повторяет
  `ArgumentError`.
- **`discard_on Klass`** останавливает сразу: строка становится
  `discarded`, с ошибкой в `last_error`, и никогда не повторяется.
- **`def retries_exhausted(error)`** выполняется, когда попытки строки
  `retry_on` исчерпаны, после того как строка действительно стала `failed`
  (никогда — для попытки, которую забрал другой обработчик: её выполнение ещё
  может удаться). Это блок `retry_on ... do |job, error|` из Rails;
  возбуждённое в нём исключение пишется в лог.
- **Восстановление** (ниже) тоже следует классу: строка класса с
  `attempts: 20`, чей процесс умер на 5-й попытке, снова ставится в очередь,
  а не помечается неудачной.

### Параллелизм по виду и по ключу

`limits_concurrency to: 1, key: "account_id"` позволяет одновременно
выполнять не больше `to:` задач этого класса во всех процессах, разделяющих
базу данных, считая отдельно для каждого значения `args["account_id"]`
(`to:` без ключа считает для всего класса; для блока то же делает
`Job.handle(kind, concurrency: n)`). Другие виды и другие ключи тем временем
продолжают выполняться. Постановка в очередь задачи с ключом, у которой в
`args` нет этого ключа, возбуждает `ArgumentError`. Ограничение считает
строки `running`, поэтому держится, пока держатся сердцебиения: задача, всё
ещё выполняющаяся после того, как её сердцебиение устарело, пересекается
со следующим выполнением восстановленной строки (см. ниже); работе, которая
никогда не должна пересекаться, нужна собственная защита.

### Задачи по расписанию

`Scheduler.every(seconds, name) { ... }` выполняет блок каждые `seconds`;
`Scheduler.cron(expr, name, ...)` — в минуты, которым соответствует
пятипольное выражение cron:

```ruby
Cybertrain::Scheduler.cron("12 * * * *", "collect prices") { Prices.collect }
Cybertrain::Scheduler.cron("0 9 * * 1-5", "morning report", tz: "Asia/Tokyo",
                           job: "MorningReportJob", args: { "scope" => "all" })
Cybertrain::Scheduler.cron("*/5 * * * *", "poll feeds", catch_up: true) { Feeds.poll }
```

- **Выражение.** Минута, час, день месяца, месяц, день недели, с `*`,
  `*/n`, `a-b`, `a,b`, `a-b/n` и именами `jan`–`dec` и `sun`–`sat` (дни
  недели `0` и `7` — воскресенье); `@hourly` и подобные не принимаются.
  Выражение, которое не разбирается или никогда не совпадает, возбуждает
  `ArgumentError` с именем задачи при загрузке `config/app.rb`, так что
  запуск останавливается.
- **Часовые пояса.** `tz:` называет пояс IANA
  ([Часовые пояса](configuration.md#time-zones)); без него задача читается
  в `scheduler_tz` (`CYBERTRAIN_SCHEDULER_TZ`, `UTC`). Время на часах,
  которое перепрыгивает переход на летнее время, в этот день не выполняется.
  В повторяющемся часе осеннего перехода выражение, чьё поле часов
  начинается с `*`, выполняется в обоих вхождениях, а выражение с
  фиксированным часом — один раз, как в Vixie cron.
- **`job:`** называет вид задачи (имя класса строкой или вид `Job.handle`),
  а `args:` — её аргументы: тогда задача по расписанию только ставит её в
  очередь, что и должна делать задача с настоящей работой. Неизвестный вид
  останавливает запуск со списком зарегистрированных.
- **Расписание** хранится в базе данных (`cybertrain_schedules`, не входит в
  `db/schema.rb`): когда каждая задача выполнялась в последний раз и когда
  выполнится в следующий. Перезапуск или другой процесс, ставший ведущим,
  продолжают с него. Задача `every`, чьё время прошло, пока ничего не
  работало, выполняется один раз при запуске; слот `cron`, пропущенный, пока
  ничего не работало, пропускается (правило cron), если только задача не
  указывает `catch_up: true` — тогда он выполняется один раз при запуске.
  Слот, наступивший, пока процессы работали, но ни один ведущий его не
  выполнил (аренда переходила из рук в руки), выполняется один раз при
  перехвате. Задача, которую вы переименовали или удалили, сохраняет свою
  строку до следующего запуска. Задача, которая ещё ни разу не выполнялась,
  следует своему текущему расписанию, когда оно наступает раньше, чем
  следующий запуск, сохранённый прежним релизом (еженедельная задача,
  ставшая ежечасной до первого запуска, выполнится в течение часа).
- **Как выполняется задача по расписанию.** Блок выполняется в потоке
  планировщика, по одной задаче за раз; каждое выполнение обёрнуто в rescue,
  который пишет в лог `[ERROR] Scheduled task "name" failed: ...`, и цикл
  продолжается. Блок не принимает аргументов (в Spinel нет `instance_eval`).
  Вызов SQLite держит свой рабочий поток ОС, пока не вернётся: при
  `SPINEL_WORKERS=1` (по умолчанию) долгий запрос к базе останавливает все
  запросы и все остальные потоки на всё это время. Отдавайте задаче по
  расписанию с настоящей работой задачу из очереди (`job:` или `Job.enqueue`
  из блока) и дробите большую работу (тысяча строк за выполнение, одна
  задача на элемент). `Cybertrain::Scheduler.last_tick` — секунда эпохи
  последнего такта, для вашей собственной проверки работоспособности.

### Страница задач и команда `jobs`

```ruby
# config/routes.rb
Cybertrain::Routes.draw do
  jobs_page "/admin/jobs", before_action: :require_admin
end
```

`jobs_page` монтирует страницу, на которой видны число строк в каждом
состоянии, число строк в очереди и ближайший срок, строки `failed` и
`discarded` (вид, аргументы, ошибка, попытки, время) и строки `running` (кто
их забрал, насколько старо их сердцебиение), по `jobs_page_per_page` (50,
`CYBERTRAIN_JOBS_PAGE_PER_PAGE`) строк в списке. Неудавшуюся строку можно
повторить (сразу снова в очередь, попытки обнулены), отбросить или удалить,
отброшенную — повторить или удалить, а все неудавшиеся строки — повторить или
отбросить разом; каждое действие трогает только строки `failed` и
`discarded`, так что строка, которую обработчик только что забрал, остаётся
нетронутой.

- Сгенерированный контроллер наследует `ApplicationController`, так что
  действуют макет, хелперы и защита CSRF приложения, а `before_action:`
  называет один из его методов: чтобы отказать, метод должен отрисовать
  ответ или перенаправить (проверка входа в приложении или проверка токена,
  как `require_admin` в examples/blog). Без `before_action:` страница открыта
  любому посетителю, и `spin run gen` печатает об этом предупреждение.
- Её кнопки — формы с токеном CSRF. Не включайте путь страницы в
  `csrf_exempt_prefixes`: под исключённым префиксом эти формы принимались бы
  с любого сайта.

Из оболочки `./<app> jobs` делает то же самое на настроенной базе данных (он
не запускает потоков):

```sh
./blog jobs list               # неудавшиеся строки, новые первыми (1000 новейших); или: list queued|running|done|discarded
./blog jobs retry 42           # или: retry --all (все неудавшиеся строки)
./blog jobs discard 42
./blog jobs delete 42
./blog jobs prune --before 30  # удаляет строки failed и discarded старше 30 дней (по умолчанию 7)
```

Строки `done` остаются, пока их что-нибудь не удалит: `Job.prune_done(before_epoch)`
из задачи по расписанию (`Cybertrain::Scheduler.cron("0 3 * * *", "prune
done jobs") { Cybertrain::Job.prune_done(Time.now.to_i - 7 * 86_400) }`).
`Job.state_count("failed")` пригодится для собственной страницы состояния.

### Несколько обработчиков, хотя бы один раз, остановка

- **Несколько обработчиков на базу.** Каждый процесс, выполняющий задачи,
  каждые `job_heartbeat_interval` (30 с) пишет сердцебиение для задач,
  которые выполняет. Строку `running`, чьё сердцебиение старше
  `job_heartbeat_stale` (процесс упал или был остановлен посреди задачи),
  снова ставит в очередь тот процесс, который посмотрит следующим, — при
  своём запуске, а затем раз в минуту, — если только эта попытка не была
  последней (большее из `job_max_attempts` и наибольшего `attempts:` класса):
  тогда строка остаётся `failed`, с `process stopped (heartbeat stale)` в
  `last_error`, чтобы задача, убивающая свой процесс, не повторялась вечно.
  Задачи по расписанию выполняются одновременно только в одном процессе:
  процессы делят аренду в базе данных (`cybertrain_leases`, продлевается на
  каждом такте, `scheduler_lease_ttl` 30 с), и только её держатель выполняет
  наступившие задачи; другой перехватывает её, когда держатель перестаёт
  продлевать. Аренда продлевается перед каждой задачей, а не во время её
  выполнения, так что задача длиннее ttl может пересечься с задачей
  следующего держателя: делайте задачи по расписанию короткими и безопасными
  для повтора. Поэтому два процесса `worker` или сервер и обработчик могут
  делить один файл SQLite; `CYBERTRAIN_WORKER=0` отключает задачи, задачи по
  расписанию и фиды в процессе `server`, который должен только обслуживать
  HTTP.
- **Хотя бы один раз.** Задача может выполниться дважды: процесс, который
  убили или который завис дольше `job_heartbeat_stale` (300 с), может всё
  ещё выполнять задачу, когда другой процесс забирает строку обратно.
  Учитывается только результат той заявки, которая держит строку
  (запоздавший результат прежней заявки отбрасывается), но побочные эффекты
  задачи случились дважды, поэтому пишите задачи, которые безопасно
  выполнить повторно (проверьте, не ушло ли уже письмо, делайте upsert, а не
  insert), как с любой очередью задач. Задача по расписанию может по той же
  причине выполниться дважды при смене ведущего.
- **Остановка.** По `SIGTERM` потоки задач перестают забирать новые задачи, а
  процесс ждёт выполняющиеся задачи до `job_drain_timeout` (10 с). Задача,
  которая к этому времени ещё выполняется, оставляет свою строку `running`;
  её сердцебиение остановилось, так что другой процесс выполнит её снова,
  когда оно устареет.
- **Тесты.** `WelcomeJob.perform_now(args)` выполняет задачу,
  `Cybertrain::Scheduler.run_due(now)` — один такт, а
  `Cybertrain::Job.work_one(now)` — одну задачу из очереди, с выбранным вами
  временем эпохи, так что тест никогда не спит;
  [Тестирование задач](testing.md#testing-jobs) описывает утверждения.

### Обновление с 0.4

- `cybertrain_jobs` получает столбец `concurrency_key` и состояние
  `discarded`; столбец добавляет первый процесс, который касается таблицы.
  Код, перечисляющий состояния (панель на основе `Job.state_count`),
  добавляет `discarded`. `Job.prune_done` по-прежнему удаляет только строки
  `done`.
- Задачи `every` после перезапуска продолжают по расписанию из базы, а не
  начинают заново: интервал, прошедший, пока процесс не работал, выполняется
  один раз при запуске.
- Если существующему виду даётся ключ (`limits_concurrency ... key:`):
  остановите все старые процессы до запуска первого нового, как при любом
  обновлении ([Роли процессов](#process-roles)). Первый новый процесс
  проставляет ключ строкам `queued`, поставленным в очередь раньше (он пишет
  в лог id строк, в полезной нагрузке которых нет этого поля), а строка
  `running`, оставленная старым процессом, получает ключ при
  восстановлении.
- `jobs` теперь встроенная команда: команду приложения с именем `jobs` нужно
  переименовать.

Не построено: приоритет задач, имена очередей и уникальность, встроенный
режим выполнения задач для тестов (тесты покрываются `perform_now` и
`perform_enqueued_jobs`). Проектное решение: `docs/design.md` D28 и D51–D53.

## Роли процессов

Один бинарный файл работает в трёх ролях. По умолчанию `./<app> server`
делает всё, как `rails server` с Solid Queue внутри Puma; две другие роли
позволяют развёртыванию разделить работу между процессами или
контейнерами — все из одного образа и с одной базой:

| Команда | Выполняет | Слушает порт |
| --- | --- | --- |
| `./<app> server [PORT]` | HTTP, [точку входа потоков](realtime.md#which-process-does-what), а если не задан `CYBERTRAIN_WORKER=0`, то задачи по расписанию, потоки задач и фиды WebSocket | да |
| `./<app> worker` | задачи по расписанию (в одном процессе за раз, благодаря аренде), потоки задач, пульс и восстановление | нет |
| `./<app> feeds [NAME...]` | [фиды WebSocket](external-services.md#consuming-websocket-feeds), все или названные | нет |

- `worker` и `feeds` печатают баннер (`=> worker: 3 job threads, 2
  scheduled tasks`), работают до `SIGTERM` или `SIGINT` (Ctrl-C), а затем останавливаются так же,
  как сервер. Свою работу они выполняют всегда: `CYBERTRAIN_WORKER=0`,
  заданный для веб-роли, их не выключает.
- `feeds` с именами запускает только эти подписки (по контейнеру на фид), а
  неизвестное имя останавливает запуск со списком зарегистрированных. Если
  фиды работают в своём процессе, задайте серверам `CYBERTRAIN_WORKER=0`,
  иначе каждый процесс получал бы каждый фид.
- Процесс `feeds` перезапускает фид, чей поток умер, и завершается со
  статусом 1, когда один и тот же фид продолжает умирать
  (`feed_restart_limit` перезапусков за `feed_restart_window`), поэтому
  запускайте его под политикой перезапуска (`restart: unless-stopped` в
  Docker, `Restart=always` в systemd); подробности — в
  [Потреблении потоков WebSocket](external-services.md#consuming-websocket-feeds).
  `./<app> feeds status` печатает последнее сообщённое состояние каждого
  фида.
- Типичное разделение: `server` с `CYBERTRAIN_WORKER=0` за прокси, один или
  несколько `worker` и `feeds`, если есть подписки. `cybertrain new` пишет
  в `config/deploy.yml` роли `web` и `worker` (и закомментированную
  `feeds`); юниты systemd — в [docs/deploy.en.md](../deploy.en.md), часть
  7, «Splitting the roles».
- **Обновление с версии без пульса**: остановите все старые процессы, прежде
  чем запускать первый новый. Новый обработчик принял бы задачи, которые
  старый ещё выполняет, за брошенные: старый процесс не пишет пульс.
- `Cybertrain::Main.worker?(ARGV)` и `Main.feeds?(ARGV)`, как и
  `Main.server?(ARGV)`, сообщают `bin/<app>.rb`, какую роль он запускает.
- `worker` требует `require "cybertrain/jobs"` в `bin/<app>.rb`, а `feeds` —
  `require "cybertrain/feeds"` (её загружает `cybertrain/websocket`); без неё
  бинарник называет недостающую строку и завершается с кодом 1.

## Хранилище кэша

`Cybertrain::Cache` хранит ответы какое-то время в собственной базе данных
приложения, чтобы следующий запрос не спрашивал медленный API снова.
`require "cybertrain"` его загружает; приложение на `cybertrain/core`
добавляет `require "cybertrain/cache"` в `bin/<app>.rb` и `bin/db.rb` или
туда, где он используется:

```ruby
require "cybertrain/cache"

text = Cybertrain::Cache.fetch("defillama/tvl", expires_in: 21_600, race_condition_ttl: 30) do
  client.get("https://api.llama.fi/tvl").body
end
data = Cybertrain::Cache.fetch_hash("prices/#{sym}", expires_in: 60) { { "usd" => price } }
count = Cybertrain::Cache.fetch_int("articles/count", expires_in: 60) { Article.count }
Cybertrain::Cache.write("import-lock", "1", expires_in: 300, unless_exist: true)   # true, если записано
```

- **Значения — это String.** `fetch(key, expires_in:, race_condition_ttl:)
  { String }` возвращает живое значение или выполняет блок и сохраняет то,
  что он вернул; `fetch_hash`, `fetch_array` и `fetch_int` хранят текст JSON
  или Integer и разбирают его на выходе, так что испорченная ячейка читается
  как `{}`, `[]` или `0`, пока не истечёт и блок не выполнится снова (в
  Spinel нет `Marshal`, а один метод возвращает один тип). Остальное —
  `read(key)` (String или nil), `write(key, value, expires_in:,
  unless_exist:)`, `delete`, `exist?`, `increment(key, by: 1, expires_in:)`
  (одна инструкция; истёкший счётчик начинается заново с `by`, а
  `expires_in:` задаёт срок только при запуске счётчика, так что счётчик на
  минуту считает именно эту минуту) и `clear`.
- **Срок жизни.** `expires_in:` задаётся в секундах; `0`, значение по
  умолчанию, никогда не истекает (отрицательное значение тоже).
  `race_condition_ttl: n`: когда строка истекла, первый вызывающий продлевает
  её на `n` секунд и вычисляет новое значение, а остальные тем временем
  продолжают читать старое, как в Rails; без этого каждый, кто обращается к
  истёкшему ключу, вычисляет сам. Блок, возбудивший исключение, ничего не
  записывает.
- **Хранение.** Строки лежат в `cybertrain_cache`, которую фреймворк создаёт
  при первом использовании и не включает в `db/schema.rb`. В памяти ничего не
  хранится: каждое чтение — это SELECT, на который SQLite отвечает из своего
  кэша страниц. Каждая запись берёт блокировку записи базы данных, которую
  ждут запросы, пишущие свои строки: кэшируйте то, что производят задачи, или
  значения, которые читаются гораздо чаще, чем меняются, а не пишите в
  нагруженном пути запроса.
- **Очистка.** Если задачи загружены, подключение файла регистрирует задачу
  по расписанию `"cybertrain cache prune"`, которая удаляет истёкшие строки
  каждые `cache_prune_interval` секунд (300, `CYBERTRAIN_CACHE_PRUNE_INTERVAL`),
  по тысяче за инструкцию. Без задач кэш чистит себя сам: первая запись
  процесса и первая запись после каждого `cache_prune_interval` удаляют до
  тысячи истёкших строк. Интервал читается при подключении файла: задайте
  переменную или `c.cache_prune_interval` в блоке `Cybertrain.configure`,
  который выполняется до require. `Cache.prune(now)` — точка входа для
  тестов.

Не построено: отдельный файл базы данных для кэша, ограничение размера,
хранилище в памяти. Проектное решение: `docs/design.md` D54.

## Консоль

`./<app> console` — это приглашение для работы с моделями приложения. В
Spinel нет `eval`, поэтому Ruby она не выполняет: она вычисляет те
выражения, которые вычисляет `<%= %>` шаблона ([язык
шаблонов](template-language.md#expressions), без блоков), плюс имена
моделей. В разработке запускайте её через
`cybertrain spin run <app> -- console`.

```console
$ ./blog console
Cybertrain console (production). Type help for commands, exit to quit.
>> Article.where(title: "Hello").count
1
>> a = Article.find(1)
#<Article id: 1, title: "Hello", body: "First post", created_at: 2026-11-05 10:00:00 UTC, updated_at: 2026-11-05 10:00:00 UTC>
>> a.update(title: "Hello again")
true
```

- Имя модели — это её relation (`Article`) с методами `where`, `where_like`,
  `order`, `limit`, `offset`, `page`, `first`, `last`, `find`, `find_by`,
  `to_a`, `count`, `exists?`, `pluck_str` / `pluck_int` / `pluck_float`,
  `sum_int`, `count_by`, `delete_all`, `to_sql` и `create`. У записи есть её
  атрибуты и методы, `update`, `save`, `destroy`, `reload`, `valid?`,
  `errors` и `attributes`. `help` перечисляет их все.
- `x = expr` сохраняет значение для следующих строк, а `_` — последнее
  значение. `sql "..."` выполняет SQL и печатает строки таблицей, экранируя
  управляющие символы в ячейках (`\e`, `\n`), так что данные не могут ни
  послать терминалу escape-последовательность, ни сломать таблицу (значение
  TEXT с байтом NUL обрезается на NUL при чтении, как при любом чтении
  сырым SQL; BLOB сохраняет все байты); `tables` перечисляет таблицы; `exit`,
  `quit` или Ctrl-D — выход.
- Строка, которая не разбирается, печатает свою ошибку, строка, возбудившая
  исключение, печатает `Class: message`, и приглашение возвращается.
  Двоичное значение печатается как `<N bytes>`.
- Записи настоящие. В продакшене консоль сначала предупреждает об этом
  баннером.

`./<app> dbconsole` открывает оболочку `sqlite3` для настроенной базы
(`CYBERTRAIN_DATABASE`), как `dbconsole` в Rails; нужна установленная
команда `sqlite3`, её код выхода передаётся дальше. Ни одна из этих команд
не запускает планировщик, задачи или фиды.

## Эксплуатация: резервные копии, VACUUM, проверка работоспособности

Данные развёрнутого приложения — это один файл SQLite, поэтому бинарный файл
содержит три инструмента эксплуатации, нужные такому приложению. Приложение с
загрузкой файлов также хранит их байты в своём корне загрузок (`upload_root`,
по умолчанию `storage/uploads/`): создавайте резервную копию этого каталога и
восстанавливайте его вместе с базой данных, иначе восстановленные записи будут
указывать на отсутствующие файлы ([Добавление загрузки файла](tutorial.md#attachments)).

**Резервные копии.** `./<app> db backup PATH` записывает согласованную копию
настроенной базы данных (`CYBERTRAIN_DATABASE`), пока сервер продолжает работать:
`VACUUM INTO` SQLite (3.27 или новее; бинарный файл это проверяет) читает один
снимок, а при WAL записи сервера тем временем продолжаются. Копия пишется во
временный файл рядом с `PATH`, создаваемый эксклюзивно с режимом 0600 (в файле
хранятся дайджесты паролей и токены сессий), сбрасывается на диск через fsync и
только затем переименовывается в `PATH`, поэтому неудачное или прерванное
копирование никогда не оставляет неполный файл под настоящим именем (временный
удаляется). Существующий `PATH` отвергается, если не передан `--force`; сама база
данных никогда не бывает целью, а база данных `:memory:` — источником.

```sh
./blog db backup /srv/blog/backups/before-upgrade.sqlite3
./blog db backup /srv/blog/backups/ --keep 14    # blog-20261025T031500Z.sqlite3, хранятся 14 самых новых
```

Цель, оканчивающаяся на `/` (или существующий каталог), получает имя с датой,
`<app>-<YYYYmmddTHHMMSSZ>.sqlite3` в UTC, в каталоге, который создаётся с
режимом 0700, если его нет; затем `--keep N` удаляет самые старые файлы ровно
такого вида сверх N и больше ничего там не трогает. Восстановление — это
копирование резервной копии поверх файла базы данных при остановленном сервере
(и удаление лежащих рядом `-wal` и `-shm` этого файла).

**VACUUM.** Удаление строк оставляет в файле свободные страницы. `./<app> db vacuum`
выполняет `VACUUM`, а затем `PRAGMA wal_checkpoint(TRUNCATE)`, поэтому
перестроенные страницы попадают в файл базы данных, файл обрезается до нового
размера, а WAL опустошается; команда выводит размер на диске (база данных плюс
WAL) до и после. `VACUUM` переписывает весь файл и всё это время держит
блокировку записи, поэтому запускайте его, когда приложение не нагружено. Если
читатель не даёт контрольной точке завершиться, команда об этом сообщает, и WAL
уменьшится на одной из следующих контрольных точек.

**Делайте резервные копии вне сервера.** Вызов SQLite удерживает свой рабочий
поток ОС до возврата, поэтому большой `VACUUM INTO` в задаче `Scheduler`
задерживал бы запросы (при `SPINEL_WORKERS=1` — все) на всё время копирования.
Вместо этого запускайте команду из cron или таймера systemd отдельным процессом:

```sh
# crontab пользователя приложения: каждую ночь в 03:15, хранить две недели
15 3 * * * cd /srv/blog/current && ./blog db backup /srv/blog/backups/ --keep 14
```

Приложение, которое хочет само делать резервные копии, может из задачи по
расписанию запустить собственный бинарный файл дочерним процессом, вместо того
чтобы выполнять SQL в своём потоке: `system` ждёт дочерний процесс только в
потоке планировщика, а запросы тем временем продолжают обслуживаться
(используйте `system` со списком аргументов, никогда — со строкой, содержащей
данные запроса). Копирование, которое длится дольше `health_worker_stale`,
заставляет проверку работоспособности отвечать `worker stale`, пока оно не
закончится.

```ruby
# config/app.rb, в обслуживающем бинарном файле, запущенном из своего каталога (dist/)
Cybertrain::Scheduler.every(86_400, "nightly backup") do
  system("./blog", "db", "backup", "storage/backups/", "--keep", "14")
end
```

**Проверка работоспособности.** Пока проверка работоспособности включена (по
умолчанию она включена; пустой `config.health_path` её отключает),
обслуживающее приложение отвечает на `GET /up` (и `HEAD`) до статических
файлов, сессии, CSRF и маршрутизатора: контроллер не участвует, никакой
`before_action` входа не может сделать редирект, и cookie не устанавливается.
Она выполняет `SELECT count(*) FROM sqlite_master`, которому приходится
прочитать страницу схемы из файла (голый `SELECT 1` его никогда не трогает), и
отвечает в `text/plain` с `Cache-Control: no-store`:

| Статус | Тело | Когда |
| --- | --- | --- |
| 200 | `ok` | запрос выполнен успешно |
| 503 | `database unavailable` | он возбудил `Cybertrain::DB::Error` (файл отсутствует или не читается, пул закрыт) |
| 503 | `worker stale` | фоновый `Scheduler` работает, и его последний такт старше `health_worker_stale` секунд (300): задача зависла или выполняется слишком долго |
| 503 | `feed stale` | [фид WebSocket](external-services.md#consuming-websocket-feeds) в этом или другом процессе не сообщал своё состояние или ничего не получал (даже pong) в течение `health_feed_stale` секунд (180); см. [Состояние фидов](realtime.md#feed-health) |

Опрос пишется в лог, как любой запрос (две строки). Путь —
`config.health_path` (`CYBERTRAIN_HEALTH_PATH`, по умолчанию `/up`; пустое
значение отключает проверку, и тогда путь, как и раньше, уходит в `public/` и
маршрутизатор). Её может опрашивать балансировщик нагрузки, kamal-proxy или
скрипт развёртывания; `public/up.html`, который пишет `cybertrain new` и
который по-прежнему опрашивает его конфигурация Kamal, показывает лишь то, что
процесс отвечает по HTTP.

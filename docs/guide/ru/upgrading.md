# Обновление

Как перевести приложение на более новый релиз CyberTrain. Порядок действий один и тот же для каждого релиза: каждый раздел ниже — один шаг, по порядку, с командой и с тем, как выглядит правильный результат. Что отдельный релиз требует сверх этого порядка, сказано в [Заметках по версиям](#notes-by-version).

## Прежде чем начать

Начните с состояния, к которому можно вернуться, на том релизе, на котором приложение работает сейчас:

```shell терминал — каталог приложения
git status --short
cybertrain version
cybertrain test
```

<!-- list: points -->
- `git status --short` ничего не печатает: всё закоммичено, поэтому каждый следующий шаг виден как отдельный diff.
- `cybertrain version` печатает релиз, на котором работает приложение. Это же значение стоит в `version` под `[lock.cybertrain]` в `spin.lock`.
- `cybertrain test` проходит. Тест, который падает сейчас, сначала чинят на старом релизе: потом его не отличить от падения, вызванного обновлением.
- У продакшена есть сегодняшняя резервная копия ([Эксплуатация: резервные копии, VACUUM, проверка работоспособности](background-and-operations.md#operations-backups-vacuum-health-check)). Релиз может изменить то, что хранится в базе данных.

Прочитайте заметки релиза, на который переходите, до того как что-либо менять. Приложение, которое пропускает релизы, читает заметки каждого промежуточного релиза, от старых к новым.

## Смените версию

Gem и фреймворк выпускаются из одного тега, и команда `cybertrain` отказывает приложению, фреймворк которого — другой релиз, чем она сама ([Перевод приложения на новый релиз](install.md#moving-an-app-to-a-new-release)). Поэтому релиз меняют в трёх местах одновременно:

1. Команда: `gem install cybertrain -v X.Y.Z`. После этого `cybertrain version` печатает `cybertrain X.Y.Z`.
2. `spin.toml`: строка `cybertrain` под `[dependencies]` называет новый тег, `ref = "vX.Y.Z"`.
3. `spin.lock`, который записывается заново с нуля:

```shell терминал — каталог приложения
rm spin.lock
cybertrain spin lock
```

Команда печатает `locked 1 package(s)`, а `git diff spin.lock` показывает новую `version` и новый `ref` (коммит тега) под `[lock.cybertrain]`. Без `rm` команда `spin lock` сохраняет уже зафиксированный коммит, и diff пуст. Приложение с другими зависимостями или зависящее от версии из индекса spin фиксирует зависимости заново так, как описано в разделе [Перевод приложения на новый релиз](install.md#moving-an-app-to-a-new-release).

Ещё два файла, записанных `cybertrain new`, называют релиз. Измените их, если они есть в приложении:

<!-- list: points -->
- `Dockerfile`: `gem install cybertrain -v X.Y.Z`. Образ собирается этой командой, и её `cybertrain build` останавливается, когда версия не та, что зафиксирована.
- `.github/workflows/ci.yml`: тег после `setup-cybertrain@` ([Непрерывная интеграция](testing.md#continuous-integration)).

Пока команда и `spin.lock` не совпадают, `server`, `build`, `db`, `test` и `generate` останавливаются с кодом выхода 1 и сообщением «`error: this application's framework is cybertrain A.B.C (spin.lock), but this cybertrain command is X.Y.Z.`» до того, как запустят spin или запишут файл. `cybertrain spin ...` никогда не проверяется.

## Установите закреплённый Spinel

Каждый релиз написан для одного релиза Spinel и компилирует приложение именно им ([Как устанавливается Spinel](install.md#how-spinel-is-installed)).

```shell терминал — любой каталог
cybertrain doctor
cybertrain setup
```

Вывод `cybertrain doctor` начинается с релиза и закреплённого за ним Spinel, `cybertrain X.Y.Z, pinned to Spinel SPINEL_TAG`, и содержит строку `spinel    ok`, когда этот Spinel установлен. Если он установлен, `cybertrain setup` печатает `nothing to install`: с этим релизом закреплённый Spinel не сменился. Если нет, `cybertrain setup` собирает новый Spinel в `~/.cybertrain/spinel/<release>/`; это занимает минуты, старый остаётся на месте, а ссылки в `~/.cybertrain/bin` указывают на новый.

Команды, которые запускают spin, сами выполняют ту же установку, когда она впервые понадобится, так что этот шаг лишь определяет, когда придётся ждать.

## Сгенерируйте код заново и прочитайте diff

Сгенерированный код в `gen/` закоммичен, и генератор нового фреймворка может записать его иначе ([Генерация кода при сборке](how-it-works.md#build-time-code-generation)):

```shell терминал — каталог приложения
SPIN_DEBUG=1 cybertrain spin run gen
git status --short gen/
git diff gen/
```

Генератор печатает `wrote` для каждого изменённого файла и `identical` для остальных. Прочитайте diff: это то, что релиз изменил в коде, который компилирует ваше приложение, и заметка версии со словами «после `spin run gen`» выполняется этим шагом. Пустой diff означает, что релиз здесь ничего не изменил.

Когда генератор отказывается принять что-то в коде приложения, он останавливается с сообщением о том, что именно. Что менять, сказано в заметках релиза; после правки запустите команду ещё раз.

## Запустите генераторы ещё раз

Код, который генератор записал в `app/`, `config/` и `test/`, принадлежит приложению, и `spin run gen` его не трогает. Генератор, который умеет привести такой код в актуальное состояние, запускают в приложении ещё раз. Сегодня это `generate authentication` — в приложении, где он использован:

```shell терминал — каталог приложения
cybertrain generate authentication > authentication.upgrade 2>&1
patch -p1 < authentication.upgrade
```

Передайте параметры, с которыми приложение было сгенерировано (`--invite-only`, `--confirmable`). Генератор пишет недостающие файлы и миграцию для недостающих столбцов, а для каждого существующего файла, который он записал бы иначе, печатает строку `manual` и diff, не меняя файл. `patch -p1` применяет эти diff-ы; diff-ы файлов, которые вы правили, примените вручную, а файлы, которые строка `manual` называет заменёнными, удалите ([Повторный запуск генератора](authentication.md#running-the-generator-again)).

Шаг выполнен, когда повторный запуск не печатает ни одной строки `manual`. Тогда удалите `authentication.upgrade`. Остальные генераторы (`scaffold`, `attachment`, `job`, `helper`, `component`) пишут только новый код; что релиз меняет в коде, записанном ими раньше, перечислено в его заметках.

## Выполните миграции

```shell терминал — каталог приложения
cybertrain db migrate
cybertrain db status
```

`db migrate` печатает `== <version> <Name>: migrating` для каждой миграции, добавленной генераторами, применяет её и заново записывает `db/schema.rb` и модели в `gen/`; после этого `db status` показывает `up` в каждой строке. Таблице, которой владеет фреймворк (`cybertrain_jobs`), миграция не нужна: первый процесс, который к ней обращается, добавляет недостающий столбец.

Релиз, меняющий способ хранения существующих данных, называет в заметках команду `db`. Выполните её здесь, на базе разработки, и ещё раз на базе продакшена во время развёртывания ([Развёртывание](#deploy)). Такую команду безопасно выполнять дважды.

## Примените заметки версии

Пройдите раздел релиза в [Заметках по версиям](#notes-by-version), тему за темой. Каждый пункт говорит, что изменилось и что с этим делать. Пункт о том, чем приложение не пользуется, ничего не требует.

Большинство пунктов находит следующий шаг — как ошибку компиляции или упавший тест. Не находит он пункты о хранимых данных, cookie, журнале и обо всём остальном, что лежит вне кода приложения: о скриптах, читающих журнал, о прокси, о мониторинге. Их проверяют чтением.

## Запустите тесты

```shell терминал — каталог приложения
cybertrain test
cybertrain build
```

`cybertrain test` компилирует тесты с новым фреймворком и проходит. `cybertrain build` компилирует бинарный файл, который работает в продакшене, `dist/<app>`, со встроенными представлениями. Настройка, которую требует новый релиз, останавливает этот бинарный файл при загрузке с сообщением, где она названа, поэтому перед развёртыванием запустите его один раз так, как это делает продакшен ([репетиция продакшена](../deploy.en.md#2-6-a-production-rehearsal)).

Затем закоммитьте всё, что изменили шаги: `spin.toml`, `spin.lock`, `gen/`, `db/`, файлы генераторов и ваши собственные правки.

## Развёртывание

В таком порядке:

1. Установите новую команду на каждой машине, которая собирает приложение (на сервере — в [руководстве по развёртыванию](../deploy.en.md#upgrading-the-framework); в `Dockerfile` — с Kamal), и выполните там `cybertrain setup`. Сборка при развёртывании останавливается, когда команда и `spin.lock` расходятся.
2. Добавьте в окружение настройки и секреты, названные в заметках ([Конфигурация и переменные окружения](configuration.md#configuration-and-environment-variables)).
3. Сделайте резервную копию.
4. Остановите все старые процессы (`server`, `worker`, `feeds`) до запуска первого нового, когда этого требуют заметки ([Роли процессов](background-and-operations.md#process-roles)).
5. Разверните как обычно: сборка, `./<app> migrate`, затем команды `db`, названные в заметках, затем новые процессы.

Чтобы вернуться назад, переключитесь на предыдущую сборку и перезапустите ([Откат](../deploy.en.md#rolling-back)). Миграции при этом не откатываются, и команда `db`, переписавшая хранимые данные, не отменяется. Если в заметках релиза не сказано, что старый релиз читает переписанные данные, возврат после такой команды означает восстановление резервной копии из шага 3.

## Какие шаги нужны релизу

Каждый шаг выполняют для каждого релиза; большинство из них заканчивается сразу, когда релизу они не нужны. Каждый шаг сам сообщает об этом:

| Шаг | Делать нечего, когда |
| --- | --- |
| Сменить версию | никогда: её меняет каждый релиз |
| Установить закреплённый Spinel | `cybertrain setup` печатает `nothing to install` |
| Сгенерировать заново | `git status --short gen/` ничего не печатает |
| Запустить генераторы ещё раз | запуск не печатает ни строки `manual`, ни строки `create` |
| Выполнить миграции | в `cybertrain db status` нет строки `down` |
| Применить заметки | у релиза нет раздела ниже |
| Тесты, развёртывание | никогда |

Патч-релиз (с `X.Y.Z` на `X.Y.Z+1`) не несёт изменений совместимости и не имеет заметок. Минорный релиз (с `X.Y` на `X.Y+1`) может их нести, и тогда у него есть раздел ниже ([контракт совместимости](../compatibility.md#changing-a-contract)).

## Заметки по версиям

Разделы после этого содержат то, что каждый релиз требует сверх порядка действий, от новых к старым. Раздел назван по двум релизам, между которыми он лежит, и разделён по темам. Заметки релиза пишутся здесь и больше нигде: руководство по теме описывает фреймворк таким, какой он есть, а порядок действий выше не называет ни одного релиза.

## С 0.4 на 0.5

### С 0.4: запросы

Что меняется для приложения, написанного для 0.4:

- Каждая сессия один раз завершается: зашифрованная cookie не читает старую подписанную, поэтому пользователи входят заново. Код, который вызывает `Session.load` или `Session.dump`, передаёт выведенный ключ, `Crypto.derive_key(secret, SessionStore::SESSION_KEY_LABEL)`; сырой секрет вызывает `Encryptor::Error`.
- Каждое приложение линкуется с OpenSSL ([Установка](install.md#requirements)); Dockerfile, ранее записанному `cybertrain new`, нужен `libssl-dev` на этапе сборки и `libssl3t64` на этапе выполнения.
- Динамический сегмент больше не захватывает `.` в маршруте, который принимает формат: id с точками требует `format: false` у своего маршрута.
- Написанная вручную лямбда `url_resolver` принимает три аргумента, `->(name, args, options)`; приложению, которое передаёт `Gen::Routes.url_resolver`, нужен только `spin run gen`.
- `params.permit` возвращает `Hash{String => Object}`: вызывайте `Cast.str` или `.to_s` на значении, прежде чем использовать его как String.
- `rate_limit` считает в кэше: `store: :memory` сохраняет прежний счётчик на процесс, двум лимитам в одном контроллере нужны свои `name:`, метод `by:`, отвечающий nil или `""`, вызывает исключение, а за методом `with:`, который ничего не рендерит, следует 429.
- Числовые хелперы вызывают исключение для значения, которое не является числом (nil в шаблоне даёт `""`, как и раньше), и для точности вне диапазона от 0 до 100.
- `include A, B` в контроллере или модели включает B первым, как Ruby; `include` модуля, который не является concern, остаётся Ruby.
- Все ETag меняются один раз (теперь в них входят формат запроса и отпечаток сборки), ответ, выбранный по `Accept`, отправляет `Vary: Accept`, а html-откат действует для любого `Accept`, где перечислены `text/html` или `*/*`. У запроса, который может получить html-откат (`application/json, text/html`), свой ETag, отличный от ETag запроса только этого формата; `text/html;q=0` в `Accept` не получает html-отката (406, если у действия есть только html), в том числе рядом с `*/*`; а `If-None-Match: *` получает 304 и от ответа, проверяемого только по `last_modified:`.
- `permit` и `expect` вызывают `ArgumentError` для фильтра, который не является Array; `layout`, называющий отсутствующий лейаут, вызывает `MissingTemplate` (лейаут `application` по умолчанию остаётся необязательным); cookie из jar больше 4096 байт вызывает `Session::CookieOverflow`.
- `public/style.css` продолжает работать; перенос в `app/assets/stylesheets/` необязателен ([Ассеты](assets.md#moving-publicstylecss)).
- Сообщения валидации берутся из встроенного словаря ([Интернационализация](i18n.md#models-and-validation-messages)) с тем же английским текстом, кроме трёх случаев: сообщение на `:base` больше не начинается с "Base", атрибут, оканчивающийся на `_id`, называется без "id" ("Article can't be blank", а не "Article id can't be blank"), а предел длины 1 читается как "1 character". Тесты, сравнивающие эти сообщения, меняются.
- `time_tag` без `format:` или с именем формата форматирует через `I18n.l` (на английской странице — тот же английский текст, что и раньше).
- gen пишет `gen/locales.rb` (пустой без `config/locales/`) и загружает `app/mailers/**/*.rb`; `cybertrain new` пишет `config/locales/en.yml`, который старое приложение может добавить.
- `allow_unauthenticated_access` теперь метод фреймворка; тот, что генератор 0.4 записал в `ApplicationController`, продолжает работать и имеет приоритет. Повторный запуск `cybertrain generate authentication` добавляет сброс пароля, блокировку, «оставаться в системе», страницу учётной записи и администраторов и печатает diff-ы для файлов, записанных 0.4 ([С 0.4: аутентификация](#from-04-authentication)).

### С 0.4: модели и база данных

Каждое изменение ниже — правка в один проход для приложения, написанного
для CyberTrain 0.4:

1. Метод чтения `has_many` возвращает relation, а не Array: добавьте `.to_a`
   перед методом, который есть только у Array (`map`, `select`, `[]`, `+`).
   Шаблоны не меняются.
2. Дата-время хранится в формате Rails: один раз после обновления запустите
   `db normalize` ([Дата-время и `db normalize`](models.md#datetimes-and-db-normalize));
   до тех пор столбец со смесью двух форматов сортируется по формату.
3. `as_json` и `to_json` пишут время как `2026-10-05T09:00:00.000Z` (было
   `2026-10-05T09:00:00Z`): снапшоты JSON в тестах меняются.
4. Атрибут `t.date` — это `Date`, а не String: `strftime` по-прежнему
   работает, для конкатенации нужен `to_s`. Столбец даты NOT NULL теперь
   проверяет присутствие.
5. Объявленный `belongs_to` без `optional: true` проверяет свой внешний
   ключ; необъявленные не меняются.
6. `where(x: a..b)` с концами Integer — условие диапазона (раньше это было
   равенство с текстом Range, которое никогда не совпадало); границы Time и
   Date используют `where_between`.
7. `Cybertrain::Cast.iso8601` — формат отображения: код, который строил им
   текст SQL, переходит на `Cast.sql_datetime`, а `Cast.binds` привязывает
   Time в хранимом формате.
8. `allow_blank: true` в строке `validates` позволяет и `presence` этой
   строки пропускать пустое значение, как в Rails (раньше относилось только к
   `length`).
9. Столбец, названный как метод, который теперь есть у каждой модели
   (`update_columns`, `destroy_dependents`, `run_custom_validations`, ...),
   генерируется как `<column>_column` ([Имена столбцов](models.md#column-names)).
10. Метод чтения `belongs_to` хранит прочитанного родителя, пока не
    изменится внешний ключ (раньше он читал его при каждом вызове): вызовите
    `reload`, чтобы увидеть изменение, сделанное другим процессом.

### С 0.4: аутентификация

Запустите `cybertrain generate authentication` ещё раз в приложении, сгенерированном 0.4 ([Запустите генераторы ещё раз](#run-the-generators-again)).

[test/fixtures/auth_04_app.upgrade.diff](../../test/fixtures/auth_04_app.upgrade.diff) — полный вывод для приложения с регистрацией, сгенерированного 0.4.

<!-- list: points -->
- Блок 0.4 в `ApplicationController` становится строкой `include Authentication`. `--force` заменяет его, только если он ровно такой, каким его написал 0.4.
- С `--confirmable` diff-ы контроллеров sessions и registrations несут строку `IMPORTANT:`: пока они не применены, неподтверждённой учётной записи не объясняют, почему она не может войти, а при регистрации ссылка не отправляется. В приложении 0.4 concern — новый файл, записанный вместе с проверкой подтверждения, так что он по-прежнему не начинает сессию для неподтверждённой учётной записи (и пишет в журнал `WARN [<request id>] no session started: user <id> has not confirmed its address`), даже если эти diff-ы так и не применят.
- При обновлении каждая сессия один раз заканчивается (cookie теперь зашифрован).

### С 0.4: конфигурация

Два значения по умолчанию изменились после 0.4
([Конфигурация и переменные окружения](configuration.md#configuration-and-environment-variables)):

- Вложенность отрисовки была неограниченной, а теперь ограничена
  `max_render_depth`, по умолчанию 12. Приложение с более глубоким деревом
  партиалов (комментарии в виде веток, меню категорий) получает ошибку шаблона,
  пока не увеличит эту настройку.
- `job_poll_interval` был равен 5 секундам, теперь 1: задачи выполняются в
  собственных потоках, и свободный поток ищет работу каждую секунду.

### С 0.4: задачи

- `cybertrain_jobs` получает столбец `concurrency_key` и состояние
  `discarded`; столбец добавляет первый процесс, который касается таблицы.
  Код, перечисляющий состояния (панель на основе `Job.state_count`),
  добавляет `discarded`. `Job.prune_done` по-прежнему удаляет только строки
  `done`.
- Задачи `every` после перезапуска продолжают по расписанию из базы, а не
  начинают заново: интервал, прошедший, пока процесс не работал, выполняется
  один раз при запуске.
- Если существующему виду даётся ключ (`limits_concurrency ... key:`):
  остановите все старые процессы до запуска первого нового, как при любом
  обновлении ([Роли процессов](background-and-operations.md#process-roles)). Первый новый процесс
  проставляет ключ строкам `queued`, поставленным в очередь раньше (он пишет
  в лог id строк, в полезной нагрузке которых нет этого поля), а строка
  `running`, оставленная старым процессом, получает ключ при
  восстановлении.
- `jobs` теперь встроенная команда: команду приложения с именем `jobs` нужно
  переименовать.

### С 0.4: журнал и отчёты об ошибках

- Каждая строка лога меняет форму: уровень в квадратных скобках в начале
  (`[INFO]`) уступает место времени, уровню и тегам,
  `2026-11-14T09:30:00.132Z INFO [<request id>] Completed 200 in 3ms`. То,
  что читает лог (grep по `[ERROR]` в скрипте, оповещение), меняется вместе с
  ним; тест, который искал строку целиком, ищет уровень и сообщение по
  отдельности (`" ERROR "` и сообщение;
  [С 0.4: тесты](#from-04-tests)).
- Каждый ответ приложения несёт `X-Request-Id` (кроме 400 и 413 сервера для
  запроса, который он не может прочитать). Прокси, который его ставил,
  видит своё значение использованным, только если прокси доверенный.
- `cybertrain_jobs` получает столбец `request_id`; его добавляет первый
  процесс, обратившийся к таблице.
- Текстовая строка лога больше не продолжается на следующих строках:
  перевод строки или возврат каретки в сообщении или теге пишется как `\n`
  или `\r`. То, что читало многострочное сообщение по нескольким строкам,
  читает экранирование.
- Столбец модели с именем `handle` теперь читается как `handle_column`:
  приложение со столбцом `users.handle` меняет вызовы `user.handle` на
  `user.handle_column` (запросы сохраняют имя SQL). Столбцы `request_id` или
  `release`, которые не текстовые, gen отклоняет
  ([Имена столбцов](models.md#column-names)).
- `cybertrain test` игнорирует экспортированные `CYBERTRAIN_LOG_FORMAT` и
  `CYBERTRAIN_SENTRY_DSN` (тесты читают текстовые строки и ничего не
  отправляют), если `config/app.rb` их не задаёт. Тесты паролей, которые пишет
  `generate authentication`, выключают строки JSON внутри своего
  `with_config`; приложение, сгенерированное раньше, чьи тесты идут с
  `log_format :json`, перезапускает генератор или переносит это изменение.
- `require "cybertrain"` теперь связывает `HttpClient` и слой TLS через
  отправитель Sentry.

### С 0.4: тесты

- Добавьте `test/test_helper.rb`
  ([Как написать тест](testing.md#writing-a-test)) и уберите из
  вспомогательного файла то, что он делал при загрузке (`AppTest.boot`,
  `BlogTest.boot`, миграцию базы): тестовая программа загружается на новой
  базе перед первым тестом, а повторная загрузка лишь отнимает время.
- Замените шаг CI `spin test` на `cybertrain test`.
- Два файла, определяющих один и тот же хелпер или константу верхнего
  уровня (по `new_client` в каждом, как их писали генераторы 0.4),
  отклоняются вместе: перенесите хелпер в `test/support/` или
  переименуйте один из них.
- Перед каждым тестом все таблицы очищаются, поэтому более поздний тест
  уже не может полагаться на строки, созданные предыдущим: перенесите
  такие данные в фикстуры или в `setup`.
- Точки подмены часов удалены: `Cybertrain::Cache.clock=`,
  `Cache.system_clock`, `RateLimit.current_time=`, `SessionStore#fixed_now=`,
  `Application.status_now=` и `Background.supervisor_clock=`. Используйте
  `travel_to`, `travel` или `freeze_time`, блок которых возвращает время
  без вашего собственного `ensure`.
- Почта в тестах хранится в `Cybertrain::Mailer.deliveries`; тест,
  читающий письма на `Test::SmtpReceiver`, сначала задаёт
  `Cybertrain.config.mail_delivery_method = :smtp`.
- Тест хелпера, написанный `generate helper` версии 0.4, определяет
  `render_inline(source)` верхнего уровня, который конфликтует с методом
  фреймворка: переименуйте его в этом файле в `render_helper_template`,
  вместе с вызовами.
- `1.month.ago` пишется `Time.current.months_ago(1)`.
- `assert_equal` падает с двухстрочным текстом Minitest; снимок
  проходящего теста не меняется.
- `cybertrain generate authentication`, запущенный снова, записывает тесты
  в форме классов и называет каждый старый файл, который они заменяют
  (`test/authentication.rb`, `test/support/app_test.rb`, ...); `--force`
  их удаляет.
- Тест, который искал строку лога целиком, с уровнем в квадратных скобках
  в начале, ищет уровень и сообщение по отдельности (`" ERROR "` и
  `"password reset mail not sent: "`): теперь строка начинается со времени и
  может нести идентификатор запроса
  ([Журнал](background-and-operations.md#logs)).
- Экспортированные `CYBERTRAIN_LOG_FORMAT` или `CYBERTRAIN_SENTRY_DSN` больше
  не доходят до тестов; чтобы тестировать с ними, задайте их в
  `config/app.rb` или присвойте DSN в тесте.

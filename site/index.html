Rails-shaped web apps, compiled to one native binary.

CyberTrain is a Rails-shaped web application framework written natively for Spinel, matz's ahead-of-time Ruby compiler. You keep the vocabulary (resources, before_action, validates, form_with, scaffolds) while cybertrain build compiles controllers, models, views and the framework itself into a single native binary with no Rack, no runtime gems and no Ruby interpreter in the artifact.

Quick start

Needs Ruby 3.2+ for the cybertrain command only (applications never run on CRuby), plus git, make, curl, a C compiler and the SQLite 3 headers: before you start. Run the build with cd dist && ./blog migrate && ./blog and CYBERTRAIN_SECRET_KEY_BASE set.

  • ServerHTTP/1.1, no Rack
  • RuntimeNo gems, no interpreter
  • DatabaseSQLite via Spinel FFI
  • CILinux and macOS

Who it is for, and what it is not

For Rails developers who want a single native binary, and who are comfortable with a young project and a Ruby subset.

  • Not Roundhouse

    Roundhouse transpiles existing Rails apps to Spinel. CyberTrain is a native framework you write directly against, not a compatibility layer.

  • Not Rails- or Rack-compatible

    No Rack compatibility and no gems at runtime: only Spinel's own spin-index packages that compile under its Ruby subset.

  • Not production-ready

    CyberTrain is pre-alpha. The example blog is exercised by CI on Linux and macOS.

01

The code you write

Rails vocabulary, with Spinel’s rules written down.

Controllers, models, routes and views read like a Rails app. Where an ahead-of-time compiler forces a difference, it is small, explicit and documented.

  • Routes

    Nested resources blocks take the mapper explicitly: articles.resources :comments.

  • Controllers

    new is written new_action: a method named new would shadow Klass.new(ctx).

  • Views

    In development, templates are read from disk, so editing a view needs no rebuild; cybertrain build embeds them in the binary. They are a closed grammar, not arbitrary Ruby.

  • Models

    class Article declares validations; columns, finders and associations are generated from db/schema.rb.

02

What works today

The Rails slice you reach for first, written natively for Spinel.

  • 01

    Native HTTP server

    Plain-Ruby HTTP/1.1 server with one green thread per connection and typed requests and responses. No Rack layer; put nginx or Caddy in front for TLS.

    TCPServer#accept

  • 02

    Routing and controllers

    resources, nested routes, before_action, after_action and rescue_from, generated into plain Ruby at build time. Strong params and flash-then-redirect work as in Rails.

    config/routes.rb

  • 03

    Sessions, flash, CSRF

    HMAC-signed cookie sessions, flash messages and CSRF protection are on by default. Forms carry the token automatically; forged posts get a 403.

    _cybertrain_session

  • 04

    ERB-flavoured templates

    Views look like Rails ERB with layouts, partials, form_with and link_to. In development they are read from disk, so edits need no rebuild. cybertrain build embeds them.

    app/views/**/*.html.erb

  • 05

    SQLite models

    Validations, callbacks and associations derived from foreign keys. Talks to SQLite through Spinel's FFI with a connection pool; every query is bound.

    ffi_func · ffi_lib

  • 06

    Migrations and scaffolds

    cybertrain generate scaffold writes migration, model, controller and five views. cybertrain db migrate generates, applies migrations, rewrites db/schema.rb and generates again.

    db/migrate/*.rb

  • 07

    Live dev loop

    cybertrain server watches your code, rebuilds in the background, then re-execs the new binary on the same port and PID. A failed build keeps the old server running.

    rebuild → stop → execv

  • 08

    Self-testing

    Write tests with Cybertrain::Test and drive the whole app in-process with a cookie-jar client. cybertrain spin test compiles each test and diffs its output.

    test/<name>.rb.expected

03

Framework and CLI

One name, two parts.

gem install cybertrain installs a command, not the framework. The framework is a Spinel package that your app depends on and compiles in. The gem gives you the cybertrain command, which creates the app, installs Spinel and runs Spinel’s tools for you.

Spinel package

The framework

The library your app is built on.

What is in it

The HTTP server, routing and controllers, sessions and CSRF protection, the template interpreter, SQLite models and migrations, and the code generator behind spin run gen.

How you get it

You don’t install it. Your app’s spin.toml names the release tag v0.2.0 of this repository, and spin lock fetches it into spin’s cache and pins the commit in spin.lock. Nothing is copied into your app.

Where it runs

Inside your app. Spinel compiles it together with your code ahead of time; it never runs on CRuby.

In dist/blog

Compiled inIt is the part of CyberTrain that ships.

RubyGem

The cybertrain command

The tool that creates, builds and runs your app.

What is in it

The cybertrain command only: new, generate scaffold, db migrate, server, build, spin, setup and doctor. Neither the framework nor Spinel is in the gem.

How you get it

gem install cybertrain. On first use it builds the pinned Spinel release, 2026.09.12, into ~/.cybertrain, unless that release is already on your PATH.

Where it runs

On your machine, under CRuby 3.2 or newer. It calls Spinel’s spin tool for you, so you don’t have to.

In dist/blog

Not shippedThe binary runs without Ruby, the gem or Spinel.

Both are released from the same tag, so their versions match: the 0.2.0 gem writes apps that depend on framework v0.2.0. To move an app to a new release, update the gem, point spin.toml at the new tag, then run cybertrain spin lock and cybertrain spin run gen.

04

How it works

The metaprogramming happens once, at build time.

Spinel compiles ahead of time and has no eval. So where Rails reaches for method_missing and define_method at runtime, spin run gen writes plain Ruby you can read and commit, and only the views are interpreted.

  1. 1

    Generate at build time

    spin run gen executes db/schema.rb and config/routes.rb to obtain table and route data, and does a lexical scan (regexes, not a parser) of app/controllers and app/models for @ivar = assignments, callback names and zero-argument defs. It writes plain, readable Ruby into gen/, including gen/views.rb, the table of embedded views (empty unless building for deployment). cybertrain db migrate, server and build run it for you.

  2. 2

    Commit gen/

    It is checked in, not gitignored, because spin build and spin test have no hook to generate first. CI re-runs spin run gen and fails on a diff, so stale generated code cannot merge. cybertrain spin run gen -- --check reports stale files.

  3. 3

    Interpret the views

    app/views/**/*.html.erb are parsed at request time and walked by a tree-walking interpreter. In development the engine reads app/views/ from disk and re-parses a template when it changes, so view edits need no rebuild. cybertrain build embeds every template in the binary (spin run gen -- --embed-views); a production binary renders only from that table and parses each template once. Spinel has no eval, so this is a closed grammar, not real Ruby.

  4. 4

    Serve with green threads, store in SQLite

    A plain-Ruby HTTP/1.1 server runs one Spinel green thread per connection. Models talk to SQLite through ffi_func/ffi_lib with a 4-connection pool (WAL, busy_timeout, foreign keys on). SPINEL_WORKERS defaults to 1.

  5. 5

    Rebuild in development

    cybertrain server runs spin run gen, then spin run blog (your app's name). In development the binary polls app/**/*.rb, config/**/*.rb, db/schema.rb and gen/**/*.rb every half second (views and gen/views.rb excluded). A change runs spin run gen && spin build blog in the background; success sets a restart flag (the one an external kill -HUP sets), and the server stops listening, drains open requests and execvs the new binary on the same port and PID. A failed build keeps serving the old binary and shows the compiler output as a banner. Rebuilds are skipped while cybertrain build holds tmp/cybertrain-build.lock. None of this loads in production.

Rails vs CyberTrain

Same vocabulary. Different rules, written down.

An ahead-of-time compiler changes a few habits. These are the ones you meet first.

Differences between Rails and CyberTrain (condensed)
TopicRailsCyberTrain
01Consolerails consoleNo console — Spinel has no eval
02ReloadingEdit code, the running app picks it upRuby needs a rebuild; cybertrain server in development does this for you (rebuild, stop, execv)
03The new actiondef newdef new_action (new would shadow Klass.new(ctx))
04Callbacksbefore_action { do_thing } (implicit self)before_action { |c| c.do_thing } — no instance_exec on a stored block, so callbacks take the controller/record explicitly
05Nested routesresources :posts do resources :comments endresources :posts do |posts| posts.resources :comments end — nested blocks take the mapper explicitly
06SessionsSession holds any marshalled objectSession values are Strings only, HMAC-signed cookie
07DatabaseMany database adaptersSQLite only, via FFI
08Testsminitest / RSpecCybertrain::Test — reflection-based runners can't work ahead-of-time

Not exhaustive.

Before you start

What you need on your machine.

Ruby
3.2+ with RubyGems, for the cybertrain command only. Applications never run on CRuby.
Spinel
2026.09.12, untested against other versions. The first command that needs it builds it into ~/.cybertrain (a few minutes, once); a spinel of that release already on PATH is used as is.
Toolchain
cc and make (Spinel compiles every program to C), plus git and curl to build Spinel. SQLite 3 headers and library: libsqlite3-dev on Debian/Ubuntu, included with Xcode command line tools on macOS. OpenSSL headers are optional.
Status
Pre-alpha, version 0.2.0, MIT licensed. The example blog is exercised by CI on Linux and macOS.

cybertrain doctor checks these tools and headers and the Spinel install, and prints the install command for your platform when one is missing. cybertrain setup installs Spinel on request and prints the PATH line for running spin yourself; cybertrain spin ARGS... runs it without one.

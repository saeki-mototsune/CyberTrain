Pré-alpha·Spinel 2026.09.12·MIT

Des applications web à la Rails, compilées en un seul binaire natif.

CyberTrain est un framework d’applications web à la Rails écrit nativement pour Spinel, le compilateur Ruby AOT de matz. Vous gardez le vocabulaire (resources, before_action, validates, form_with, scaffolds), tandis que cybertrain build compile les contrôleurs, les modèles, les vues et le framework lui-même en un seul binaire natif, sans Rack, sans gems à l’exécution et sans interpréteur Ruby dans l’artefact.

Commencer→ Essayer dans le navigateur Voir sur GitHub

Démarrage rapide

Nécessite Ruby 3.2+ pour la commande cybertrain uniquement (les applications ne tournent jamais sur CRuby), ainsi que git, make, curl, un compilateur C et les en-têtes SQLite 3 : avant de commencer. Lancez le build avec cd dist && ./blog migrate && ./blog, en définissant CYBERTRAIN_SECRET_KEY_BASE.

  • ServeurHTTP/1.1, sans Rack
  • ExécutionNi gems, ni interpréteur
  • Base de donnéesSQLite via la FFI de Spinel
  • CILinux et macOS

Pour qui, et ce que ce n’est pas

Pour les développeurs Rails qui veulent un seul binaire natif et qui s’accommodent d’un projet jeune et d’un sous-ensemble de Ruby.

  • Pas Roundhouse

    Roundhouse transpile des applications Rails existantes vers Spinel. CyberTrain est un framework natif pour lequel vous écrivez directement votre code, pas une couche de compatibilité.

  • Pas compatible Rails ni Rack

    Aucune compatibilité Rack et aucune gem à l’exécution : uniquement les paquets spin-index propres à Spinel qui compilent avec son sous-ensemble de Ruby.

  • Pas prêt pour la production

    CyberTrain est en pré-alpha. Le blog d’exemple est testé par la CI sous Linux et macOS.

01

Votre code

Le vocabulaire de Rails, avec les règles de Spinel écrites noir sur blanc.

Contrôleurs, modèles, routes et vues se lisent comme une application Rails. Là où un compilateur AOT impose une différence, elle est minime, explicite et documentée.

  • Routes

    Les blocs resources imbriqués reçoivent le mapper explicitement : articles.resources :comments.

  • Contrôleurs

    new s’écrit new_action : une méthode nommée new masquerait Klass.new(ctx).

  • Vues

    En développement, les templates sont lus depuis le disque, donc modifier une vue ne demande pas de recompilation ; cybertrain build les intègre au binaire. Ils forment une grammaire fermée, pas du Ruby arbitraire.

  • Modèles

    class Article déclare les validations ; les colonnes, les finders et les associations sont générés à partir de db/schema.rb.

02

Ce qui fonctionne

La partie de Rails dont vous vous servez en premier, écrite nativement pour Spinel.

  • 01

    Serveur HTTP natif

    Serveur HTTP/1.1 en Ruby pur, avec un green thread par connexion et des requêtes et réponses typées. Pas de couche Rack ; placez nginx ou Caddy devant pour le TLS.

    TCPServer#accept

  • 02

    Routage et contrôleurs

    resources, routes imbriquées, before_action, after_action et rescue_from, générés en Ruby pur à la compilation. Les strong params et le flash suivi d’une redirection fonctionnent comme dans Rails.

    config/routes.rb

  • 03

    Sessions, flash, CSRF

    Les sessions par cookie signé HMAC, les messages flash et la protection CSRF sont activés par défaut. Les formulaires portent le jeton automatiquement ; les POST falsifiés reçoivent une 403.

    _cybertrain_session

  • 04

    Templates façon ERB

    Les vues ressemblent à de l’ERB Rails, avec layouts, partiels, form_with et link_to. En développement, elles sont lues depuis le disque, donc les modifications ne demandent pas de recompilation. cybertrain build les intègre.

    app/views/**/*.html.erb

  • 05

    Modèles SQLite

    Validations, callbacks et associations déduites des clés étrangères. Dialogue avec SQLite via la FFI de Spinel, avec un pool de connexions ; chaque requête utilise des paramètres liés.

    ffi_func · ffi_lib

  • 06

    Migrations et scaffolds

    cybertrain generate scaffold écrit la migration, le modèle, le contrôleur et cinq vues. cybertrain db migrate génère, applique les migrations, réécrit db/schema.rb et génère à nouveau.

    db/migrate/*.rb

  • 07

    Boucle de dev à chaud

    cybertrain server surveille votre code, recompile en arrière-plan, puis ré-exécute (exec) le nouveau binaire sur le même port et avec le même PID. Un build échoué laisse tourner l’ancien serveur.

    rebuild → stop → execv

  • 08

    Tests intégrés

    Écrivez des tests avec Cybertrain::Test et pilotez toute l’application dans le même processus avec un client doté d’une cookie jar. cybertrain spin test compile chaque test et compare (diff) sa sortie.

    test/<name>.rb.expected

03

Framework et CLI

Un nom, deux parties.

gem install cybertrain installe une commande, pas le framework. Le framework est un paquet Spinel dont votre application dépend et qu’elle compile avec elle. La gem vous fournit la commande cybertrain, qui crée l’application, installe Spinel et lance les outils de Spinel pour vous.

Paquet Spinel

Le framework

La bibliothèque sur laquelle repose votre application.

Contenu

Le serveur HTTP, le routage et les contrôleurs, les sessions et la protection CSRF, l’interpréteur de templates, les modèles SQLite et les migrations, ainsi que le générateur de code derrière spin run gen.

Comment l’obtenir

Vous ne l’installez pas. Le spin.toml de votre application désigne le tag de version v0.2.1 de ce dépôt, et spin lock le récupère dans le cache de spin et épingle le commit dans spin.lock. Rien n’est copié dans votre application.

Où il s’exécute

Dans votre application. Spinel le compile à l’avance avec votre code ; il ne tourne jamais sur CRuby.

Dans dist/blog

Compilé dedansC’est la partie de CyberTrain qui est livrée.

RubyGem

La commande cybertrain

L’outil qui crée, compile et lance votre application.

Contenu

Uniquement la commande cybertrain : new, generate scaffold, db migrate, server, build, spin, setup et doctor. Ni le framework ni Spinel ne sont dans la gem.

Comment l’obtenir

gem install cybertrain. À la première utilisation, elle compile la version épinglée de Spinel, 2026.09.12, dans ~/.cybertrain, sauf si cette version est déjà dans votre PATH.

Où elle s’exécute

Sur votre machine, sous CRuby 3.2 ou plus récent. Elle appelle l’outil spin de Spinel pour vous, pour que vous n’ayez pas à le faire.

Dans dist/blog

Non livréeLe binaire tourne sans Ruby, sans la gem et sans Spinel.

Les deux sont publiés à partir du même tag, leurs versions correspondent donc : la gem 0.2.1 crée des applications qui dépendent du framework v0.2.1. Pour passer une application à une nouvelle version, mettez à jour la gem, faites pointer spin.toml vers le nouveau tag, puis lancez cybertrain spin lock et cybertrain spin run gen.

04

Fonctionnement

La métaprogrammation a lieu une seule fois, à la compilation.

Spinel compile à l’avance et n’a pas d’eval. Là où Rails recourt à method_missing et à define_method à l’exécution, spin run gen écrit donc du Ruby pur que vous pouvez lire et commiter, et seules les vues sont interprétées.

  1. 1

    Générer à la compilation

    spin run gen exécute db/schema.rb et config/routes.rb pour obtenir les données des tables et des routes, et effectue un balayage lexical (des regex, pas un parseur) de app/controllers et app/models à la recherche d’affectations @ivar =, de noms de callbacks et de def sans argument. Il écrit du Ruby pur et lisible dans gen/, y compris gen/views.rb, la table des vues intégrées (vide, sauf lors d’un build pour le déploiement). cybertrain db migrate, server et build le lancent pour vous.

  2. 2

    Commiter gen/

    Il est versionné, et non ignoré par git, car spin build et spin test n’ont pas de hook pour générer d’abord. La CI relance spin run gen et échoue en cas de diff : du code généré périmé ne peut donc pas être fusionné. cybertrain spin run gen -- --check signale les fichiers périmés.

  3. 3

    Interpréter les vues

    Les app/views/**/*.html.erb sont analysés au moment de la requête et parcourus par un interpréteur d’arbre (tree-walking). En développement, le moteur lit app/views/ depuis le disque et réanalyse un template quand il change, donc modifier une vue ne demande pas de recompilation. cybertrain build intègre tous les templates au binaire (spin run gen -- --embed-views) ; un binaire de production ne fait le rendu qu’à partir de cette table et n’analyse chaque template qu’une fois. Spinel n’a pas d’eval, il s’agit donc d’une grammaire fermée, pas de vrai Ruby.

  4. 4

    Servir avec des green threads, stocker dans SQLite

    Un serveur HTTP/1.1 en Ruby pur exécute un green thread Spinel par connexion. Les modèles dialoguent avec SQLite via ffi_func/ffi_lib, avec un pool de 4 connexions (WAL, busy_timeout, clés étrangères activées). SPINEL_WORKERS vaut 1 par défaut.

  5. 5

    Recompiler en développement

    cybertrain server lance spin run gen, puis spin run blog (le nom de votre application). En développement, le binaire inspecte app/**/*.rb, config/**/*.rb, db/schema.rb et gen/**/*.rb toutes les demi-secondes (hors vues et gen/views.rb). Un changement lance spin run gen && spin build blog en arrière-plan ; en cas de succès, un indicateur de redémarrage est levé (celui que lève un kill -HUP externe), puis le serveur cesse d’écouter, termine les requêtes en cours et fait un execv du nouveau binaire sur le même port et avec le même PID. Un build échoué continue de servir l’ancien binaire et affiche la sortie du compilateur dans un bandeau. Les recompilations sont ignorées tant que cybertrain build détient tmp/cybertrain-build.lock. Rien de tout cela n’est chargé en production.

05

Rails vs CyberTrain

Même vocabulaire. Des règles différentes, écrites noir sur blanc.

Un compilateur AOT change quelques habitudes. Voici celles que vous rencontrerez en premier.

Différences entre Rails et CyberTrain (version condensée)
SujetRailsCyberTrain
01Consolerails consolePas de console — Spinel n’a pas d’eval
02RechargementModifiez le code, l’application en cours d’exécution le prend en compteLe Ruby demande une recompilation ; en développement, cybertrain server s’en charge pour vous (recompilation, arrêt, execv)

04Callbacksbefore_action { do_thing } (self implicite)before_action { |c| c.do_thing } — pas d’instance_exec sur un bloc stocké, donc les callbacks reçoivent explicitement le contrôleur/l’enregistrement

06

Performances

Sur un cœur, 2,3 à 8,2 fois plus de requêtes que Rails.

examples/blog face au même blog écrit en Rails 8.1 : mêmes vues, routes, modèles et schéma SQLite. Les deux tournent en mode production, épinglés sur les mêmes cœurs d’une même machine, sous la même charge envoyée par wrk. Un second cœur profite surtout à Rails : Puma ajoute tout un processus, alors que le second thread de travail de CyberTrain n’ajoute que 18 à 84 %, si bien que sur deux cœurs l’écart est de 2,3 à 4,6 fois.

  • Mémoire sous charge

    10,5 Mo

    Rails : 131 Mo, un processus Puma à 3 threads.

  • Du lancement à la première réponse

    0,02 s

    Rails : 1,2 s.

  • Ce qu’il faut sur le serveur

    2,5 Mo

    Un seul binaire. Rails : 109 Mo de Ruby, de 69 gems et de l’application.

  • Le prix : une compilation

    2 min

    pour compiler le binaire avec cybertrain build. Rails exécute ses sources telles quelles.

Médianes de trois mesures de 10 secondes après un échauffement, sur une VM cloud à 4 vCPU, wrk tournant sur les deux cœurs que le serveur n’utilise pas : CyberTrain 0.2.1 compilé par Spinel 2026.09.12, face à Rails 8.1.4 sur Ruby 3.4.6 avec YJIT et Puma 8.0 (un processus à 3 threads sur un cœur, deux sur deux cœurs). Les barres d’une même ligne partagent une échelle. Une requête à la fois, la page d’un article répond en 0,6 ms contre 3,7 ms. Avec jemalloc des deux côtés (l’image de production de Rails le précharge ; pour CyberTrain, c’est une ligne dans spin.toml), un cœur donne 2,8 à 10,1 fois. Une partie de l’écart vient de ce que Rails fait par défaut et CyberTrain non : il chiffre le cookie de session et signe un jeton CSRF par formulaire. La méthode, tous les chiffres et comment relancer la mesure : docs/benchmark.md.

07

Avant de commencer

Ce qu’il vous faut sur votre machine.

Ruby
3.2+ avec RubyGems, uniquement pour la commande cybertrain. Les applications ne tournent jamais sur CRuby.
Spinel
2026.09.12, non testé avec d’autres versions. La première commande qui en a besoin le compile dans ~/.cybertrain (quelques minutes, une seule fois) ; un spinel de cette version déjà présent dans le PATH est utilisé tel quel.
Outils
cc et make (Spinel compile chaque programme en C), plus git et curl pour compiler Spinel. En-têtes et bibliothèque SQLite 3 : libsqlite3-dev sous Debian/Ubuntu, inclus avec les Command Line Tools de Xcode sous macOS. Les en-têtes OpenSSL sont facultatifs.
Statut
Pré-alpha, version 0.2.1, sous licence MIT. Le blog d’exemple est testé par la CI sous Linux et macOS.

cybertrain doctor vérifie ces outils et en-têtes ainsi que l’installation de Spinel, et affiche la commande d’installation pour votre plateforme quand l’un d’eux manque. cybertrain setup installe Spinel à la demande et affiche la ligne PATH pour lancer spin vous-même ; cybertrain spin ARGS... le lance sans cette ligne.

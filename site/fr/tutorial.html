00Prérequis

PourquoiCyberTrain compile via Spinel vers du C : il lui faut donc une chaîne de compilation C et les en-têtes SQLite ; la commande cybertrain est une gem, il lui faut donc Ruby.

  • Ruby 3.2+ et RubyGems, uniquement pour la commande cybertrain ; les applications ne tournent jamais sur CRuby.
  • Spinel 2026.09.12, non testé avec d’autres versions. Vous ne l’installez pas à la main : la première commande qui en a besoin compile cette version dans ~/.cybertrain (quelques minutes, une seule fois), sauf si un spinel de cette version est déjà dans le PATH.
  • Une chaîne de compilation C (cc, ou le compilateur désigné par CC) et make, plus git et curl, pour compiler Spinel, qui compile chaque programme en C.
  • En-têtes et bibliothèque SQLite 3 : libsqlite3-dev sous Debian/Ubuntu ; fournis avec les Command Line Tools de Xcode sous macOS.
  • Les en-têtes OpenSSL (libssl-dev) sont facultatifs : sans eux, Spinel est compilé sans son paquet openssl, que CyberTrain n’utilise pas.

cybertrain doctor vérifie ces outils et en-têtes ainsi que l’installation de Spinel ; quand un élément requis manque, il affiche aussi la commande d’installation pour votre plateforme.

Comment CyberTrain installe SpinelCe qui se passe la première fois qu’une commande a besoin de spin

cybertrain new, db, server, build et spin cherchent d’abord Spinel 2026.09.12 : un spinel et un spin de cette version déjà dans le PATH, sinon la copie sous ~/.cybertrain/spinel/2026.09.12/, sinon ils compilent cette copie à partir du tag de version de Spinel (git clone, make deps, make -j, make install), une seule fois, en quelques minutes. Le journal est ~/.cybertrain/log/spinel-2026.09.12-build.log ; s’il manque un outil nécessaire à la compilation, cybertrain indique lequel et affiche la commande d’installation pour votre plateforme avant de commencer.

cybertrain setup fait la même chose à la demande (--force recompile la copie sous ~/.cybertrain) et, quand c’est sa propre copie qui est utilisée, affiche la ligne qui la place dans votre PATH, pour lancer spin vous-même :

~/.cybertrain/bin contient des liens spinel et spin vers la version utilisée. S’il n’est pas dans le PATH, cybertrain spin ARGS... lance spin avec cette version depuis n’importe quel répertoire. CYBERTRAIN_HOME remplace ~/.cybertrain, et CYBERTRAIN_SPINEL_HOME=PREFIX utilise à la place le Spinel installé dans PREFIX (ce doit être cette version). Un spinel d’une autre version présent dans le PATH n’est jamais utilisé ni modifié.

Pas de machine sur laquelle installer ? Le bac à sable ouvre ce blog dans un GitHub Codespace avec les étapes 02, 03, 04 et 07 déjà faites.

01Installer la CLI

Pourquoicybertrain est la commande qui crée les applications, génère les scaffolds de ressources, migre, sert et compile.

La première ligne l’installe depuis RubyGems. Le reste est le tutoriel entier en un coup d’œil ; les étapes ci-dessous le reprennent une commande à la fois.

La commande cybertrain est en Ruby pur et la gem l’exécute sous CRuby (3.2 ou plus récent) ; ni le framework ni Spinel ne sont dans la gem. Ses commandes (cybertrain help les affiche) :

  • cybertrain new NAME [--path DIR | --version V | --git URL [--ref R]] [--skip-spin] crée une application dans NAME, puis y lance spin lock et spin run gen, en installant d’abord Spinel si nécessaire.
  • cybertrain generate scaffold NAME field:type ... (alias g scaffold) ajoute une ressource à l’application du répertoire courant.
  • cybertrain db migrate génère, applique les migrations en attente, puis génère à nouveau (spin run gen; spin run db -- migrate; spin run gen) ; cybertrain migration est conservé comme alias.
  • cybertrain db COMMAND... lance toute autre commande de base de données après spin run gen : status, rollback [N] (qui génère à nouveau ensuite), schema:dump, create.
  • cybertrain server [PORT] génère, puis démarre le serveur de développement (spin run gen; spin run NAME, ou spin run NAME -- PORT ; port 3000 par défaut).
  • cybertrain build compile NAME avec app/views/ intégré et assemble dist/ (le binaire, public/, storage/, tmp/).
  • cybertrain spin ARGS... lance spin avec le Spinel épinglé, depuis n’importe quel répertoire : cybertrain spin test, cybertrain spin run gen -- --check.
  • cybertrain setup [--force] installe Spinel 2026.09.12 dans ~/.cybertrain, sauf si un spinel de cette version est déjà dans le PATH ; --force recompile la copie sous ~/.cybertrain.
  • cybertrain doctor vérifie la chaîne de compilation C, les en-têtes SQLite et l’installation de Spinel.
  • cybertrain version affiche la version (cybertrain 0.2.1) ; cybertrain help affiche l’aide.

db, server et build s’exécutent dans une application ; NAME est le [package] name de son spin.toml.

Si Spinel ou l’une des deux étapes spin échoue, les fichiers restent en place, new sort avec le code 1 et affiche ce qu’il faut lancer une fois la cause corrigée (pour Spinel : cybertrain setup, puis cybertrain spin lock && cybertrain spin run gen dans le nouveau répertoire). --skip-spin se contente d’écrire les fichiers ; --path DIR fait plutôt dépendre l’application d’une copie locale du dépôt, --git URL [--ref R] du framework situé à URL (à la branche ou au tag R), et --version V d’une version de l’index, une fois que cybertrain sera sur un spin-index.

06Le contrôleur ArticlesController

PourquoiUn CRUD complet, à la Rails jusqu’aux strong params et au flash suivi d’une redirection, à deux choses près que Spinel impose partout.

Règle Spinel

new_action, pas new

Une méthode nommée littéralement new masquerait ArticlesController.new(ctx), que le framework utilise pour construire le contrôleur. La route GET /articles/new y mène toujours ; vous renommez seulement la méthode. La vue reste new.html.erb et render :new ne change pas.

Règle Spinel

Les callbacks reçoivent le contrôleur explicitement

Il n’y a pas d’instance_exec sur un bloc stocké, donc un callback sous forme de bloc reçoit le contrôleur (ou l’enregistrement) en argument : before_action { |c| c.do_thing }, et non before_action { do_thing }. Les actions et les callbacks sont appelés par leur nom littéral, jamais via send.

Le scaffold écrit le contrôleur complet, avec aussi index, show, edit, update et destroy ; l’extrait ci-dessus les omet. Dans index, @articles = Article.all.to_a : le .to_a est obligatoire.

Les variables d’instance sont trouvées par un balayage lexical des @ivar = : relancez donc cybertrain spin run gen après en avoir ajouté une ; le serveur de développement le fait pour vous.

07Générer, migrer, lancer

PourquoiTransformer le schéma et les routes en gen/, créer la base SQLite, démarrer le serveur.

spin run gen lit db/schema.rb et config/routes.rb, analyse app/ et écrit gen/ ; spin run db -- migrate applique db/migrate/*.rb et réécrit db/schema.rb. L’ordre compte : le premier spin run gen place la nouvelle migration dans gen/migrations.rb, que requiert bin/db.rb, et le second construit les modèles à partir du db/schema.rb réécrit.

cybertrain server affiche chaque commande spin qu’il lance, puis la bannière de démarrage de l’application. Le premier démarrage compile l’application, il prend donc un moment :

  • Relancez cybertrain spin run gen et commitez gen/ après avoir modifié le schéma, les routes, ou les callbacks et ivars d’un contrôleur ou d’un modèle. Le serveur de développement le fait pour vous.
  • Changez le port avec cybertrain server 4000 (ou PORT=4000).
  • cybertrain db ajoute le -- dont spin run db a besoin avant ses arguments ; cybertrain db status et les autres commandes de base de données fonctionnent de la même façon.

Règle Spinel

Il n’y a pas de console

rails console n’a pas d’équivalent : Spinel n’a pas d’eval. Les modifications Ruby demandent une recompilation, que cybertrain server fait pour vous en développement (recompilation, arrêt, execv). En développement, les vues sont analysées depuis le disque à chaque requête, donc en modifier une ne demande pas de recompilation ; cybertrain build les intègre pour la production.

Règle Spinel

Les vues forment une grammaire fermée, pas du Ruby

Spinel n’a pas d’eval, les templates sont donc interprétés selon une grammaire fixe. link_to n’a pas d’option method: ; utilisez button_to. each accepte un ou deux paramètres de bloc. Un commentaire de locals stricts comme <%# locals: (comment:) %> n’accepte pas de valeurs par défaut. Un partiel reçoit une copie de l’environnement de l’appelant, donc @article est visible dans comments/_form.

12Tester

Pourquoiminitest et RSpec trouvent les tests par réflexion, ce qu’un compilateur AOT ne peut pas faire ; CyberTrain fournit donc Cybertrain::Test.

Un test de modèle

Assertions : assert, refute, assert_equal, assert_nil, assert_includes, assert_raises("Class") { }, flunk. L’exemple utilise aussi assert_response et assert_redirected_to.

Un parcours HTTP complet

Cybertrain::Test::Client pilote une application dans le même processus (sans socket) avec une cookie jar, de sorte que les sessions et le CSRF se comportent comme derrière un navigateur. Les requêtes sans le jeton reçoivent une 403.

Avant de compiler

Ce que les fragments omettent

  • support/blog_test correspond à examples/blog/test/support/blog_test.rb : copiez-le dans le test/support/ de votre application, où les fichiers sont requis, pas exécutés. Il migre une base storage/test.sqlite3 neuve, démarre l’application sous le nom BLOG, charge Cybertrain::Test et son client, et vous fournit BlogTest.form_token (le jeton CSRF du dernier formulaire rendu) et BlogTest.article_path.
  • Terminez le fichier par Cybertrain::Test.run!, qui lance les tests et affiche les lignes que compare le snapshot.
  • Définissez c.log_level = :none if c.test? dans config/app.rb pour garder les logs de requêtes hors de la sortie comparée.

Lancer les tests

cybertrain spin test lance spin test avec le Spinel épinglé ; avec la chaîne d’outils dans le PATH (étape 00), spin test fait la même chose. Il compile chaque test/*.rb en un programme distinct et compare (diff) sa sortie (stdout et stderr ensemble) à un snapshot test/<name>.rb.expected versionné. Les fichiers de test/support/ sont requis, pas exécutés. Pour écrire un snapshot :

--regen écrit le snapshot à partir de la sortie de CRuby. Les tests qui accèdent à SQLite via FFI ne peuvent pas tourner sous CRuby : leur snapshot vient donc du binaire compilé (la deuxième ligne ci-dessus). cybertrain spin test sort avec un code non nul tant qu’un snapshot est périmé, il est donc suivi de ; et non de && ; la vérification [ -x ] saute la capture si la compilation a échoué, ce qui conserve l’ancien snapshot. Les tests qui ne peuvent pas tourner sous CRuby ont besoin de ce snapshot avant que cybertrain spin test puisse réussir ; les autres tests sans snapshot sont comparés à la sortie de CRuby.

13Compiler pour le déploiement

PourquoiUne seule commande compile l’application dans un dossier dist/ déployable, avec toutes les vues intégrées.

Elle écrit dist/ : le binaire de l’application avec toutes les vues intégrées, plus les fichiers qu’il utilise, à côté de lui. Elle lance spin run gen -- --embed-views, spin build blog et spin run gen (qui remet en place le gen/views.rb versionné et vide, même après un échec ou un Ctrl-C), puis assemble :

  • dist/blogle framework compilé, les contrôleurs, les modèles et l’interpréteur de templates, avec toutes les vues intégrées
  • dist/public/ressources statiques et pages d’erreur, ou laissez un reverse proxy le servir
  • dist/storage/créé vide ; contient le fichier SQLite par défaut (une recompilation ne le vide jamais)
  • dist/tmp/créé vide (une recompilation ne le vide jamais)

Copiez dist/ sur une machine avec le même OS et le même CPU (le binaire est lié à la SQLite du système) et lancez-le là-bas. Un binaire compilé est en mode production par défaut (CYBERTRAIN_ENV permet de le changer). Définissez CYBERTRAIN_SECRET_KEY_BASE ; à titre d’illustration :

./blog migrate applique les migrations compilées dans le binaire, et ./blog db status affiche leur état ; PORT définit le port. Gardez le même secret d’un redémarrage à l’autre : le changer met fin à toutes les sessions.

Cybertrain::Config lit d’abord l’environnement ; config/app.rb a le dernier mot :

  • Le serveur parle du HTTP/1.1 simple : placez nginx ou Caddy devant pour le TLS et HTTP/2. Le cookie de session est Secure en production, servez donc l’application en HTTPS (ne définissez c.session_secure = false dans config/app.rb que si la production est vraiment en http simple).
  • En production, l’application refuse de démarrer sans CYBERTRAIN_SECRET_KEY_BASE.
  • En production, une exception renvoie une 500, et une réponse d’erreur brute (la 404 en texte brut du routeur, head :not_found, render plain:) est remplacée par public/<status>.html quand ce fichier existe ; cybertrain new écrit 404.html et 500.html.
  • SIGTERM cesse d’accepter des connexions, laisse se terminer les requêtes en cours et quitte quand elles sont terminées, ou après le drain_timeout du serveur (10 s).
  • La surveillance des fichiers et la boucle de recompilation ne tournent jamais en production. Un cybertrain server en cours d’exécution saute ses recompilations tant que cybertrain build détient tmp/cybertrain-build.lock.

+Bon à savoir

PourquoiDes limites et particularités à connaître avant qu’elles ne vous surprennent.

  • Les sessions ne contiennent que des String, dans un cookie signé HMAC.
  • SQLite uniquement, via la FFI de Spinel.
  • Pas de backtraces : les erreurs affichent la classe, le message, la ligne de requête et le nom/la ligne du template.
  • Un attribut mal orthographié dans une vue s’affiche vide au lieu de lever une erreur ; c’est une lacune connue.
  • Les associations viennent uniquement des clés étrangères du schéma ; pas de has_many :through, includes, pluck, dependent:, d’enums, de STI ni d’associations polymorphes.
  • Pas de namespace, de respond_to/formats, de constraints ni de mount ; render json: est minimal.
  • Dans un modèle généré par scaffold, seul le premier champ string reçoit une validation de présence par défaut.
  • Le générateur utilise un balayage lexical (des regex), pas un parseur, sur app/controllers et app/models.
  • Les vues sont intégrées à la compilation : une modification qui ne touche que les vues nécessite cybertrain build et un redémarrage avant d’atteindre la production.
  • Compilez dist/ sur le même OS et le même CPU que la machine qui l’exécute : le binaire est lié à la SQLite du système.
  • SPINEL_WORKERS vaut 1 par défaut.
  • Seul Spinel 2026.09.12 est testé.

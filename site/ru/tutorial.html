00Требования

ЗачемCyberTrain компилируется через Spinel в C, поэтому ему нужны инструменты C и заголовки SQLite; команда cybertrain — это гем, поэтому ей нужен Ruby.

  • Ruby 3.2+ и RubyGems — только для команды cybertrain; приложения никогда не запускаются на CRuby.
  • Spinel 2026.09.12; с другими версиями не тестировался. Вручную его устанавливать не нужно: первая команда, которой он нужен, собирает этот релиз в ~/.cybertrain (несколько минут, один раз), если spinel этого релиза ещё нет в PATH.
  • Инструменты C (cc или компилятор, указанный в CC) и make, а также git и curl — для сборки Spinel, который компилирует каждую программу в C.
  • Заголовки и библиотека SQLite 3: libsqlite3-dev в Debian/Ubuntu; на macOS входят в Xcode command line tools.
  • Заголовки OpenSSL (libssl-dev) необязательны: без них Spinel собирается без своего пакета openssl, который CyberTrain не использует.

cybertrain doctor проверяет эти инструменты и заголовки, а также установку Spinel; если чего-то обязательного не хватает, она также выводит команду установки для вашей платформы.

Как CyberTrain устанавливает SpinelЧто происходит, когда команде впервые нужен spin

cybertrain new, db, server, build и spin сначала ищут Spinel 2026.09.12: spinel и spin этого релиза, уже доступные в PATH; иначе — копию в ~/.cybertrain/spinel/2026.09.12/; иначе собирают эту копию из релизного тега Spinel (git clone, make deps, make -j, make install) — один раз, за несколько минут. Лог пишется в ~/.cybertrain/log/spinel-2026.09.12-build.log; если не хватает инструмента, нужного для сборки, cybertrain ещё до её начала сообщает, какого именно, и выводит команду установки для вашей платформы.

cybertrain setup делает то же самое по запросу (--force пересобирает копию в ~/.cybertrain) и, если используется именно её копия, выводит строку, добавляющую её в ваш PATH, чтобы запускать spin самостоятельно:

В ~/.cybertrain/bin лежат ссылки spinel и spin на используемый релиз. Если этого каталога нет в PATH, cybertrain spin ARGS... запускает spin этого релиза из любого каталога. CYBERTRAIN_HOME заменяет ~/.cybertrain, а CYBERTRAIN_SPINEL_HOME=PREFIX вместо этого использует Spinel, установленный в PREFIX (это должен быть тот же релиз). spinel другого релиза в PATH никогда не используется и не затрагивается.

Негде устанавливать? Песочница открывает этот блог в GitHub Codespace, где шаги 02, 03, 04 и 07 уже выполнены.

01Установка CLI

Зачемcybertrain — команда, которая создаёт приложения, генерирует скаффолды ресурсов, выполняет миграции, запускает сервер и собирает.

Первая строка устанавливает её из RubyGems. Остальное — весь учебник в двух словах; шаги ниже разбирают его по одной команде.

Команда cybertrain написана на обычном Ruby, и гем запускает её под CRuby (3.2 или новее); ни фреймворка, ни Spinel в геме нет. Её команды (их выводит cybertrain help):

  • cybertrain new NAME [--path DIR | --version V | --git URL [--ref R]] [--skip-spin] создаёт приложение в NAME, затем запускает в нём spin lock и spin run gen, при необходимости сначала устанавливая Spinel.
  • cybertrain generate scaffold NAME field:type ... (псевдоним g scaffold) добавляет ресурс в приложение в текущем каталоге.
  • cybertrain db migrate выполняет генерацию, применяет ожидающие миграции и генерирует снова (spin run gen; spin run db -- migrate; spin run gen); cybertrain migration оставлена как псевдоним.
  • cybertrain db COMMAND... после spin run gen запускает любую другую команду базы данных: status, rollback [N] (после которой генерация выполняется снова), schema:dump, create.
  • cybertrain server [PORT] выполняет генерацию, затем запускает сервер разработки (spin run gen; spin run NAME или spin run NAME -- PORT; порт по умолчанию — 3000).
  • cybertrain build собирает NAME со встроенными app/views/ и формирует dist/ (бинарный файл, public/, storage/, tmp/).
  • cybertrain spin ARGS... запускает spin с зафиксированным Spinel из любого каталога: cybertrain spin test, cybertrain spin run gen -- --check.
  • cybertrain setup [--force] устанавливает Spinel 2026.09.12 в ~/.cybertrain, если spinel этого релиза ещё нет в PATH; --force пересобирает копию в ~/.cybertrain.
  • cybertrain doctor проверяет инструменты C, заголовки SQLite и установку Spinel.
  • cybertrain version выводит версию (cybertrain 0.2.1); cybertrain help выводит справку по использованию.

db, server и build запускаются внутри приложения; NAME — это [package] name из его spin.toml.

06ArticlesController

ЗачемПолный CRUD в духе Rails, вплоть до strong params и связки «flash, затем редирект», — за исключением двух вещей, которые Spinel навязывает везде.

Правило Spinel

new_action, а не new

Метод, буквально названный new, затенил бы ArticlesController.new(ctx), с помощью которого фреймворк создаёт контроллер. Маршрут GET /articles/new по-прежнему ведёт к нему; вы лишь переименовываете метод. Представление по-прежнему называется new.html.erb, а render :new не меняется.

Правило Spinel

Колбэки получают контроллер явно

Для сохранённого блока нет instance_exec, поэтому колбэк-блок получает контроллер (или запись) как аргумент: before_action { |c| c.do_thing }, а не before_action { do_thing }. Действия и колбэки вызываются по их буквальному имени, никогда через send.

Скаффолд создаёт полный контроллер, включая также index, show, edit, update и destroy; во фрагменте выше они опущены. В index — @articles = Article.all.to_a: .to_a обязателен.

Переменные экземпляра находятся лексическим сканированием @ivar =, поэтому после добавления новой заново запустите cybertrain spin run gen; сервер разработки делает это за вас.

07Генерация, миграции, запуск

ЗачемПревратить схему и маршруты в gen/, создать базу данных SQLite, запустить сервер.

spin run gen читает db/schema.rb и config/routes.rb, сканирует app/ и записывает gen/; spin run db -- migrate применяет db/migrate/*.rb и перезаписывает db/schema.rb. Порядок важен: первый spin run gen помещает новую миграцию в gen/migrations.rb, который подключает bin/db.rb, а второй строит модели по перезаписанному db/schema.rb.

cybertrain server выводит каждую запускаемую команду spin, а затем стартовый баннер приложения. При первом запуске приложение компилируется, так что это займёт некоторое время:

  • Заново запускайте cybertrain spin run gen и коммитьте gen/ после изменения схемы, маршрутов или колбэков и переменных экземпляра контроллера либо модели. Сервер разработки делает это за вас.
  • Порт меняется так: cybertrain server 4000 (или PORT=4000).
  • cybertrain db добавляет --, который нужен spin run db перед аргументами; cybertrain db status и другие команды базы данных работают так же.

Правило Spinel

Консоли нет

У rails console нет аналога: в Spinel нет eval. Изменения в Ruby требуют пересборки, которую в режиме разработки за вас выполняет cybertrain server (пересборка, остановка, execv). В режиме разработки представления разбираются с диска при каждом запросе, поэтому правка представления не требует пересборки; для продакшена cybertrain build встраивает их в бинарный файл.

[@article, comment], и form_with(model: [@article, @comment]) разрешаются по одному и тому же правилу [parent, child]: новый дочерний объект направляется во вложенную коллекцию (article_comments_path), сохранённый — во вложенный элемент (article_comment_path); эти хелперы генерируются в gen/routes.rb из вложенного блока resources выше.

Правило Spinel

Представления — замкнутая грамматика, а не Ruby

В Spinel нет eval, поэтому шаблоны интерпретируются по фиксированной грамматике. У link_to нет опции method:; используйте button_to. each принимает один или два параметра блока. Комментарий strict locals вроде <%# locals: (comment:) %> не допускает значений по умолчанию. Партиал получает копию окружения вызывающего кода, поэтому @article виден в comments/_form.

12Тестирование

Зачемminitest и RSpec находят тесты через рефлексию, на которую AOT-компилятор не способен, поэтому CyberTrain поставляется с Cybertrain::Test.

Тест модели

Утверждения: assert, refute, assert_equal, assert_nil, assert_includes, assert_raises("Class") { }, flunk. В примере также используются assert_response и assert_redirected_to.

Полный HTTP-сценарий

Cybertrain::Test::Client прогоняет приложение внутри процесса (без сокета) с хранилищем cookie, поэтому сессии и CSRF ведут себя так же, как за браузером. Запросы без токена получают 403.

Чтобы скомпилировалось

Что опущено в отрывках

  • support/blog_test — это examples/blog/test/support/blog_test.rb: скопируйте его в test/support/ вашего приложения, где файлы подключаются, а не запускаются. Он применяет миграции к новой storage/test.sqlite3, загружает приложение как BLOG, подключает Cybertrain::Test и его клиент и предоставляет BlogTest.form_token (CSRF-токен последней отрендеренной формы) и BlogTest.article_path.
  • Завершите файл вызовом Cybertrain::Test.run!: он запускает тесты и выводит строки, которые сравниваются со снимком.
  • Задайте c.log_level = :none if c.test? в config/app.rb, чтобы логи запросов не попадали в сравниваемый вывод.

Запуск тестов

cybertrain spin test запускает spin test с зафиксированным Spinel; если инструменты есть в PATH (шаг 00), то же самое делает spin test. Он компилирует каждый test/*.rb в отдельную программу и сравнивает её вывод (stdout и stderr вместе) с закоммиченным снимком test/<name>.rb.expected. Файлы в test/support/ подключаются, а не запускаются. Чтобы записать снимок:

--regen записывает снимок по выводу CRuby. Тесты, обращающиеся к SQLite через FFI, не могут работать под CRuby, поэтому их снимок берётся из скомпилированного бинарного файла (вторая строка выше). Пока снимок устарел, cybertrain spin test завершается с ненулевым кодом, поэтому после него стоит ;, а не &&; проверка [ -x ] пропускает запись, если компиляция не удалась, и старый снимок сохраняется. Тестам, которые не могут работать под CRuby, этот снимок нужен, прежде чем cybertrain spin test сможет пройти; остальные тесты без снимка сравниваются с выводом CRuby.

13Сборка для развёртывания

ЗачемОдна команда собирает приложение в готовый к развёртыванию каталог dist/ со всеми встроенными представлениями.

Она записывает dist/: бинарный файл приложения со всеми встроенными представлениями и рядом с ним файлы, которые он использует. Она запускает spin run gen -- --embed-views, spin build blog и spin run gen (который возвращает закоммиченный пустой gen/views.rb, даже после сбоя или Ctrl-C), а затем собирает:

  • dist/blogскомпилированные фреймворк, контроллеры, модели и интерпретатор шаблонов со всеми встроенными представлениями
  • dist/public/статические ресурсы и страницы ошибок; можно отдавать их через обратный прокси
  • dist/storage/создаётся пустым; по умолчанию здесь файл SQLite (пересборка никогда его не очищает)
  • dist/tmp/создаётся пустым (пересборка никогда его не очищает)

Скопируйте dist/ на машину с той же ОС и тем же процессором (бинарный файл компонуется с системной SQLite) и запустите там. Собранный бинарный файл по умолчанию работает в окружении production (CYBERTRAIN_ENV переопределяет это). Задайте CYBERTRAIN_SECRET_KEY_BASE; для примера:

./blog migrate применяет миграции, вкомпилированные в бинарный файл, а ./blog db status показывает их состояние; PORT задаёт порт. Не меняйте секрет между перезапусками: его смена завершает все сессии.

  • Сервер говорит на обычном HTTP/1.1: для TLS и HTTP/2 поставьте перед ним nginx или Caddy. В production cookie сессии имеет флаг Secure, поэтому отдавайте приложение по HTTPS (задавайте c.session_secure = false в config/app.rb, только если production действительно работает по обычному http).
  • Без CYBERTRAIN_SECRET_KEY_BASE production отказывается запускаться.
  • В production исключение даёт ответ 500, а голый ответ с ошибкой (текстовый 404 маршрутизатора, head :not_found, render plain:) заменяется на public/<status>.html, если такой файл существует; cybertrain new создаёт 404.html и 500.html.
  • SIGTERM прекращает приём соединений, даёт выполняющимся запросам завершиться и выходит, когда они закончатся, или по истечении drain_timeout сервера (10 с).
  • Слежение за файлами и цикл пересборки никогда не работают в production. Запущенный cybertrain server пропускает пересборки, пока cybertrain build удерживает tmp/cybertrain-build.lock.

+Что нужно знать

ЗачемОграничения и особенности, о которых лучше знать заранее, чтобы они не застали вас врасплох.

  • Сессии хранят только строки (String) в cookie с подписью HMAC.
  • Только SQLite, через FFI Spinel.
  • Бэктрейсов нет: ошибки показывают класс, сообщение, строку запроса и имя/строку шаблона.
  • Атрибут с опечаткой в представлении выводится пустым вместо исключения; это известный пробел.
  • Ассоциации выводятся только из внешних ключей схемы; нет has_many :through, includes, pluck, dependent:, enum, STI и полиморфных ассоциаций.
  • Нет namespace, respond_to/форматов, constraints и mount; render json: минимален.
  • В модели, созданной скаффолдом, валидацию присутствия по умолчанию получает только первое строковое поле.
  • Генератор обрабатывает app/controllers и app/models лексическим сканированием (регулярными выражениями), а не парсером.
  • Представления встраиваются при сборке: даже изменение только в представлении требует cybertrain build и перезапуска, прежде чем оно попадёт в production.
  • Собирайте dist/ на той же ОС и том же процессоре, что и у машины, где он будет работать: бинарный файл компонуется с системной SQLite.
  • SPINEL_WORKERS по умолчанию равен 1.
  • Протестирован только Spinel 2026.09.12.

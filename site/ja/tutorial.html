00Requirements

WhyCyberTrain compiles through Spinel to C, so it needs a C toolchain and the SQLite headers; the cybertrain command is a gem, so it needs Ruby.

  • Ruby 3.2+ and RubyGems, for the cybertrain command only; applications never run on CRuby.
  • Spinel 2026.09.12, untested against other versions. You do not install it by hand: the first command that needs it builds that release into ~/.cybertrain (a few minutes, once), unless a spinel of that release is already on PATH.
  • A C toolchain (cc, or the compiler CC names) and make, plus git and curl, to build Spinel, which compiles every program to C.
  • SQLite 3 headers and library: libsqlite3-dev on Debian/Ubuntu; present with Xcode's command line tools on macOS.
  • OpenSSL headers (libssl-dev) are optional: without them Spinel builds without its openssl package, which CyberTrain does not use.

cybertrain doctor checks these tools and headers and the Spinel install; when a required one is missing it also prints the install command for your platform.

How CyberTrain installs SpinelWhat happens the first time a command needs spin

cybertrain new, db, server, build and spin first look for Spinel 2026.09.12: a spinel and spin of that release already on PATH, else the copy under ~/.cybertrain/spinel/2026.09.12/, else they build that copy from the Spinel release tag (git clone, make deps, make -j, make install), once, in a few minutes. The log is ~/.cybertrain/log/spinel-2026.09.12-build.log; if a tool the build needs is missing, cybertrain says which and prints the install command for your platform before it starts.

cybertrain setup does the same on request (--force rebuilds the copy under ~/.cybertrain) and, when its own copy is the one in use, prints the line that puts it on your PATH, for running spin yourself:

~/.cybertrain/bin holds spinel and spin links to the release in use. Without it on PATH, cybertrain spin ARGS... runs spin with that release from any directory. CYBERTRAIN_HOME replaces ~/.cybertrain, and CYBERTRAIN_SPINEL_HOME=PREFIX uses the Spinel installed in PREFIX instead (it must be that release). A spinel of another release on PATH is never used or touched.

No machine to install on? The playground opens this blog in a GitHub Codespace with steps 02, 03, 04 and 07 already done.

01Install the CLI

Whycybertrain is the command that creates apps, scaffolds resources, migrates, serves and builds.

The first line installs it from RubyGems. The rest is the whole tutorial at a glance; the steps below take it one command at a time.

The cybertrain command is plain Ruby and the gem runs it under CRuby (3.2 or newer); neither the framework nor Spinel is in the gem. Its commands (cybertrain help prints them):

  • cybertrain new NAME [--path DIR | --version V | --git URL [--ref R]] [--skip-spin] creates an application in NAME, then runs spin lock and spin run gen in it, installing Spinel first when it is needed.
  • cybertrain generate scaffold NAME field:type ... (alias g scaffold) adds a resource to the application in the current directory.
  • cybertrain db migrate generates, applies pending migrations, and generates again (spin run gen; spin run db -- migrate; spin run gen); cybertrain migration is kept as an alias.
  • cybertrain db COMMAND... runs any other database command after spin run gen: status, rollback [N] (which generates again afterwards), schema:dump, create.
  • cybertrain server [PORT] generates, then starts the development server (spin run gen; spin run NAME, or spin run NAME -- PORT; default port 3000).
  • cybertrain build builds NAME with app/views/ embedded and assembles dist/ (the binary, public/, storage/, tmp/).
  • cybertrain spin ARGS... runs spin with the pinned Spinel, from any directory: cybertrain spin test, cybertrain spin run gen -- --check.
  • cybertrain setup [--force] installs Spinel 2026.09.12 into ~/.cybertrain unless a spinel of that release is already on PATH; --force rebuilds the copy under ~/.cybertrain.
  • cybertrain doctor checks the C toolchain, the SQLite headers and the Spinel install.
  • cybertrain version prints the version (cybertrain 0.2.1); cybertrain help prints the usage.

db, server and build run inside an application; NAME is the [package] name in its spin.toml.

02Create the application

WhyYou get the Rails directory conventions plus three bin/ programs: bin/blog.rb (the app), bin/gen.rb (the generator) and bin/db.rb (development migrations).

cybertrain new writes the application with its spin.toml pointing at the release matching the CLI:

Then it makes sure Spinel is installed (the first time, that means building Spinel 2026.09.12 into ~/.cybertrain: a few minutes, once; see step 00) and runs spin lock (spin fetches the framework into its cache, ~/.cache/spin/packages/, and pins the commit in spin.lock) and spin run gen, much as rails new runs bundle install, so cybertrain server works right away. It ends by printing the next steps. Nothing of the framework is copied into the app; commit spin.toml and spin.lock.

If Spinel or one of the two spin steps fails, the files stay, new exits with 1 and prints what to run once the cause is fixed (for Spinel: cybertrain setup, then cybertrain spin lock && cybertrain spin run gen in the new directory). --skip-spin only writes the files; --path DIR depends on a local checkout instead, --git URL [--ref R] on the framework at URL (at branch or tag R), and --version V on an index version once cybertrain is on a spin-index.

App names use lowercase letters, digits and _, starting with a letter. The generated tree:

bin/blog.rb is the application's one entry point, the program spin build blog compiles: ./blog serves, ./blog migrate and ./blog db status manage the database. bin/gen.rb runs the generator (spin run gen), and bin/db.rb runs the migrator during development (cybertrain db migrate uses it, since bin/blog.rb cannot compile until the first migration has generated gen/models/). gen/ already holds views.rb, the committed, empty table of embedded views.

06The ArticlesController

WhyFull CRUD, Rails-shaped down to strong params and flash-then-redirect, except for two things Spinel forces everywhere.

Spinel rule

new_action, not new

A method literally named new would shadow ArticlesController.new(ctx), which the framework uses to construct the controller. The route GET /articles/new still maps to it; you only rename the method. The view is still new.html.erb and render :new is unchanged.

Spinel rule

Callbacks take the controller explicitly

There is no instance_exec on a stored block, so a block callback receives the controller (or the record) as an argument: before_action { |c| c.do_thing }, not before_action { do_thing }. Actions and callbacks are called by their literal name, never send.

The scaffold writes the full controller with index, show, edit, update and destroy too; the excerpt above omits them. In index, @articles = Article.all.to_a: the .to_a is required.

Instance variables are found by a lexical scan of @ivar =, so re-run cybertrain spin run gen after adding one; the development server does this for you.

You are here:Build time, then run time · gen/ → build/bin/blog

07Generate, migrate, run

WhyTurn schema and routes into gen/, create the SQLite database, start the server.

spin run gen reads db/schema.rb and config/routes.rb, scans app/ and writes gen/; spin run db -- migrate applies db/migrate/*.rb and rewrites db/schema.rb. The order matters: the first spin run gen puts the new migration into gen/migrations.rb, which bin/db.rb requires, and the second builds the models from the rewritten db/schema.rb.

cybertrain server prints each spin command it runs, then the app's boot banner. The first start compiles the app, so it takes a while:

  • Re-run cybertrain spin run gen and commit gen/ after touching the schema, routes, or a controller's or model's callbacks and ivars. The development server does this for you.
  • Change the port with cybertrain server 4000 (or PORT=4000).
  • cybertrain db adds the -- that spin run db needs before its arguments; cybertrain db status and the other database commands work the same way.

Spinel rule

There is no console

rails console has no counterpart: Spinel has no eval. Ruby changes need a rebuild, which cybertrain server does for you in development (rebuild, stop, execv). In development views are parsed from disk per request, so editing one needs no rebuild; cybertrain build embeds them for production.

09Nest the routes

WhyRails' guide nests comments under articles.

Spinel rule

Nested blocks take the mapper explicitly

Write resources :articles do |articles| and articles.resources :comments, not a bare resources :comments. Spinel's instance_eval trampoline only rewires self for the outermost block.

Spinel rule

Views are a closed grammar, not Ruby

Spinel has no eval, so templates are interpreted against a fixed grammar. link_to has no method: option; use button_to. each takes one or two block parameters. A strict-locals comment such as <%# locals: (comment:) %> takes no default values. A partial gets a copy of the caller's environment, so @article is visible in comments/_form.

12Test it

Whyminitest and RSpec find tests by reflection, which an ahead-of-time compiler cannot do, so CyberTrain ships Cybertrain::Test.

A model test

Assertions: assert, refute, assert_equal, assert_nil, assert_includes, assert_raises("Class") { }, flunk. The example also uses assert_response and assert_redirected_to.

A full HTTP flow

Cybertrain::Test::Client drives an app in-process (no socket) with a cookie jar, so sessions and CSRF behave as behind a browser. Requests without the token get a 403.

Before it compiles

What the snippets leave out

  • support/blog_test is examples/blog/test/support/blog_test.rb: copy it into your app’s test/support/, where files are required, not run. It migrates a fresh storage/test.sqlite3, boots the app as BLOG, loads Cybertrain::Test and its client, and gives you BlogTest.form_token (the CSRF token of the last rendered form) and BlogTest.article_path.
  • End the file with Cybertrain::Test.run!, which runs the tests and prints the lines the snapshot compares.
  • Set c.log_level = :none if c.test? in config/app.rb to keep request logs out of the compared output.

Run the tests

cybertrain spin test runs spin test with the pinned Spinel; with the toolchain on PATH (step 00), spin test does the same. It compiles each test/*.rb into its own program and diffs its output (stdout and stderr together) against a committed test/<name>.rb.expected snapshot. Files in test/support/ are required, not run. To write a snapshot:

--regen writes the snapshot from CRuby's output. Tests that touch SQLite through FFI can't run under CRuby, so their snapshot comes from the compiled binary (the second line above). cybertrain spin test exits non-zero while a snapshot is stale, so it is followed by ;, not &&; the [ -x ] check skips the capture when the compile failed, so the old snapshot is kept. Tests that cannot run under CRuby need this snapshot before cybertrain spin test can pass; other tests without a snapshot are compared with CRuby's output.

13Build for deployment

WhyOne command builds the app into a deployable dist/ folder, with every view embedded.

This writes dist/: the app binary with every view embedded, plus the files it uses beside it. It runs spin run gen -- --embed-views, spin build blog and spin run gen (which puts the committed, empty gen/views.rb back, even after a failure or Ctrl-C), then assembles:

  • dist/blogthe compiled framework, controllers, models and template interpreter, with every view embedded
  • dist/public/static assets and error pages, or let a reverse proxy serve it
  • dist/storage/created empty; the SQLite file by default (a rebuild never empties it)
  • dist/tmp/created empty (a rebuild never empties it)

Copy dist/ to a machine with the same OS and CPU (the binary links the system SQLite) and run it there. A built binary is production by default (CYBERTRAIN_ENV overrides). Set CYBERTRAIN_SECRET_KEY_BASE; for illustration:

./blog migrate applies the migrations compiled into the binary, and ./blog db status shows their status; PORT sets the port. Keep the secret the same across restarts: changing it ends every session.

Cybertrain::Config reads the environment first; config/app.rb overrides:

  • The server speaks plain HTTP/1.1: put nginx or Caddy in front for TLS and HTTP/2. The session cookie is Secure in production, so serve it over HTTPS (set c.session_secure = false in config/app.rb only if production really is plain http).
  • Production refuses to start without CYBERTRAIN_SECRET_KEY_BASE.
  • In production an exception answers 500, and a bare error response (the router's plain-text 404, head :not_found, render plain:) is replaced by public/<status>.html when that file exists; cybertrain new writes 404.html and 500.html.
  • SIGTERM stops accepting, lets requests in flight finish and exits when they are done, or after the server's drain_timeout (10 s).
  • The watcher and rebuild loop never run in production. A running cybertrain server skips its rebuilds while cybertrain build holds tmp/cybertrain-build.lock.

+Things to know

WhyLimits and quirks worth knowing before they surprise you.

  • Sessions hold Strings only, in an HMAC-signed cookie.
  • SQLite only, through Spinel’s FFI.
  • No backtraces: errors show class, message, request line and template name/line.
  • A misspelled attribute in a view renders blank instead of raising; this is a known gap.
  • Associations come from schema foreign keys only; no has_many :through, includes, pluck, dependent:, enums, STI or polymorphic associations.
  • No namespace, respond_to/formats, constraints or mount; render json: is minimal.
  • Only the first string field gets a default presence validation in a scaffolded model.
  • The generator uses a lexical scan (regexes), not a parser, over app/controllers and app/models.
  • Views are embedded at build time: a view-only change needs cybertrain build and a restart before it reaches production.
  • Build dist/ on the same OS and CPU as the machine that runs it: the binary links the system SQLite.
  • SPINEL_WORKERS defaults to 1.
  • Only Spinel 2026.09.12 is tested.

+Differences from Rails

WhyThe full table from the README, in one place.

Differences between Rails and CyberTrain (full table from the README)
RailsCyberTrain
rails consoleNo console — Spinel has no eval
Edit code, the running app picks it upRuby needs a rebuild; cybertrain server in development does this for you (rebuild, stop, execv)
Edit a view, no reload neededSame — views are parsed from disk per request in development
def newdef new_action (new would shadow Klass.new(ctx))
before_action { do_thing } (implicit self)before_action { |c| c.do_thing } — no instance_exec on a stored block, so callbacks take the controller/record explicitly
resources :posts do resources :comments endresources :posts do |posts| posts.resources :comments end — nested blocks take the mapper explicitly
ERB compiles to a method; any object, any methodInterpreted against a fixed grammar/dispatch table
Session holds any marshalled objectSession values are Strings only, HMAC-signed cookie
Many database adaptersSQLite only, via FFI
has_many :through, includes, pluck, dependent:, enums, STI, polymorphic associationsNot implemented; associations come from schema foreign keys only
namespace, format/respond_to, constraints, mountNot implemented — flat names, render json: only
Full backtrace on an exceptionClass, message, request line, template name/line — Spinel exposes no backtraces
Rack, its middleware, and any gem in a GemfileNo Rack compatibility; a small fixed middleware set; Spinel's own spin-index, limited to what compiles under its Ruby subset
minitest / RSpecCybertrain::Test — reflection-based runners can't work ahead-of-time
Auth, mailers, jobs, ActionCable, asset pipeline, i18nNot built (outside the MVP)

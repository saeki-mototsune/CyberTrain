プレアルファ·Spinel 2026.09.12·MIT

Rails 流の Web アプリを、ひとつのネイティブバイナリに。

CyberTrain は、matz による Ruby の AOT コンパイラである Spinel のためにネイティブに書かれた、Rails 流の Web アプリケーションフレームワークです。語彙（resources、before_action、validates、form_with、スキャフォールド）はそのままに、cybertrain build がコントローラー、モデル、ビュー、そしてフレームワーク自体をひとつのネイティブバイナリにコンパイルします。成果物には Rack も、実行時の gem も、Ruby インタプリタも含まれません。

はじめる→ ブラウザで試す GitHub で見る

クイックスタート

Ruby 3.2+ が必要なのは cybertrain コマンドだけです（アプリケーションが CRuby 上で動くことはありません）。ほかに git、make、curl、C コンパイラ、SQLite 3 のヘッダーが必要です：始める前に。ビルドしたものは、cd dist && ./blog migrate && ./blog で、CYBERTRAIN_SECRET_KEY_BASE を設定して実行します。

  • サーバーHTTP/1.1、Rack なし
  • ランタイムgem なし、インタプリタなし
  • データベースSpinel FFI 経由の SQLite
  • CILinux と macOS

誰のためのものか、何ではないか

ひとつのネイティブバイナリを求める Rails 開発者のうち、若いプロジェクトと Ruby のサブセットを受け入れられる人のためのものです。

  • Roundhouse ではない

    Roundhouse は既存の Rails アプリを Spinel 向けにトランスパイルします。CyberTrain は、それに対して直接コードを書くネイティブなフレームワークであり、互換レイヤーではありません。

  • Rails・Rack 互換ではない

    Rack 互換性はなく、実行時に gem も使えません。使えるのは Spinel 独自の spin-index のパッケージのうち、その Ruby サブセットでコンパイルできるものだけです。

  • 本番運用には未対応

    CyberTrain はプレアルファです。サンプルのブログは Linux と macOS の CI で検証されています。

01

書くコード

Rails の語彙のまま、Spinel のルールは明文化。

コントローラー、モデル、ルーティング、ビューは Rails アプリと同じように読めます。AOT コンパイラのために違いが生じる箇所は、小さく、明示的で、ドキュメント化されています。

  • ルーティング

    ネストした resources ブロックはマッパーを明示的に受け取ります：articles.resources :comments。

  • コントローラー

    new は new_action と書きます。new という名前のメソッドは Klass.new(ctx) を覆い隠してしまうからです。

  • ビュー

    開発環境ではテンプレートをディスクから読み込むので、ビューの編集に再ビルドは不要です。cybertrain build はテンプレートをバイナリに埋め込みます。テンプレートは閉じた文法であり、任意の Ruby ではありません。

  • モデル

    class Article ではバリデーションを宣言します。カラム、ファインダー、関連付けは db/schema.rb から生成されます。

02

現在できること

最初に手に取る Rails の機能を、Spinel 向けにネイティブで。

  • 01

    ネイティブ HTTP サーバー

    素の Ruby で書かれた HTTP/1.1 サーバーで、接続ごとにグリーンスレッドを 1 本使い、リクエストとレスポンスは型付きです。Rack 層はありません。TLS には前段に nginx か Caddy を置きます。

    TCPServer#accept

  • 02

    ルーティングとコントローラー

    resources、ネストしたルーティング、before_action、after_action、rescue_from は、ビルド時に素の Ruby として生成されます。Strong Parameters や、フラッシュを設定してからのリダイレクトも Rails と同じように動きます。

    config/routes.rb

  • 03

    セッション、フラッシュ、CSRF

    HMAC 署名付き cookie によるセッション、フラッシュメッセージ、CSRF 保護がデフォルトで有効です。フォームには自動でトークンが含まれ、偽造された POST には 403 が返ります。

    _cybertrain_session

  • 04

    ERB 風のテンプレート

    ビューは Rails の ERB と同じ見た目で、レイアウト、パーシャル、form_with、link_to が使えます。開発環境ではディスクから読み込むので、編集しても再ビルドは不要です。cybertrain build はビューを埋め込みます。

    app/views/**/*.html.erb

  • 05

    SQLite のモデル

    バリデーション、コールバック、外部キーから導出される関連付け。Spinel の FFI 経由で、コネクションプールを使って SQLite とやり取りします。クエリはすべてパラメータをバインドします。

    ffi_func · ffi_lib

  • 06

    マイグレーションとスキャフォールド

    cybertrain generate scaffold はマイグレーション、モデル、コントローラー、5 つのビューを書き出します。cybertrain db migrate は生成を行い、マイグレーションを適用して db/schema.rb を書き換え、もう一度生成します。

    db/migrate/*.rb

  • 07

    ライブ開発ループ

    cybertrain server はコードを監視してバックグラウンドで再ビルドし、新しいバイナリを同じポート・同じ PID で再 exec します。ビルドに失敗した場合は古いサーバーが動き続けます。

    rebuild → stop → execv

  • 08

    組み込みのテスト

    Cybertrain::Test でテストを書き、cookie jar 付きのクライアントでアプリ全体をプロセス内で動かします。cybertrain spin test は各テストをコンパイルし、その出力の差分を取ります。

    test/<name>.rb.expected

03

フレームワークと CLI

ひとつの名前、ふたつの部品。

gem install cybertrain でインストールされるのはコマンドであり、フレームワークではありません。フレームワークは Spinel パッケージで、アプリがこれに依存し、アプリに組み込んでコンパイルします。gem が提供するのは cybertrain コマンドで、アプリの作成、Spinel のインストール、Spinel のツールの実行を代わりに行います。

Spinel パッケージ

フレームワーク

アプリの土台となるライブラリ。

中身

HTTP サーバー、ルーティングとコントローラー、セッションと CSRF 保護、テンプレートインタプリタ、SQLite のモデルとマイグレーション、そして spin run gen の裏で動くコードジェネレーター。

入手方法

インストールは不要です。アプリの spin.toml がこのリポジトリのリリースタグ v0.2.1 を指定し、spin lock がそれを spin のキャッシュに取得して、コミットを spin.lock に固定します。アプリには何もコピーされません。

動く場所

アプリの中です。Spinel があなたのコードと一緒に事前（AOT）コンパイルします。CRuby 上で動くことはありません。

dist/blog には

組み込み済みCyberTrain のうち、出荷されるのはこの部分です。

RubyGem

cybertrain コマンド

アプリを作成し、ビルドし、実行するツール。

中身

cybertrain コマンドだけです：new、generate scaffold、db migrate、server、build、spin、setup、doctor。フレームワークも Spinel も gem には含まれません。

入手方法

gem install cybertrain です。初回使用時に、固定された Spinel のリリース 2026.09.12 を ~/.cybertrain にビルドします（そのリリースがすでに PATH 上にある場合を除く）。

動く場所

手元のマシン上で、CRuby 3.2 以降で動きます。Spinel の spin ツールを代わりに呼び出すので、自分で呼ぶ必要はありません。

dist/blog には

含まれないバイナリは Ruby、gem、Spinel なしで動きます。

両者は同じタグからリリースされるため、バージョンは一致します：0.2.1 の gem は、フレームワーク v0.2.1 に依存するアプリを書き出します。アプリを新しいリリースに移行するには、gem を更新し、spin.toml を新しいタグに向けてから、cybertrain spin lock と cybertrain spin run gen を実行します。

04

仕組み

メタプログラミングは一度だけ、ビルド時に。

Spinel は事前（AOT）コンパイルを行い、eval を持ちません。そのため、Rails が実行時に method_missing や define_method を使う場面では、spin run gen が読んでコミットできる素の Ruby を書き出し、インタプリタで解釈するのはビューだけです。

  1. 1

    ビルド時に生成する

    spin run gen は db/schema.rb と config/routes.rb を実行してテーブルとルートのデータを取得し、app/controllers と app/models を字句的にスキャン（パーサーではなく正規表現）して、@ivar = の代入、コールバック名、引数なしの def を見つけます。そして読みやすい素の Ruby を gen/ に書き出します。これには埋め込みビューのテーブルである gen/views.rb も含まれます（デプロイ用にビルドするとき以外は空です）。cybertrain db migrate、server、build がこれを代わりに実行します。

  2. 2

    gen/ をコミットする

    spin build と spin test には先に生成を行うフックがないため、gitignore せずにリポジトリに含めます。CI は spin run gen を再実行し、差分があれば失敗するので、古い生成コードがマージされることはありません。cybertrain spin run gen -- --check は古くなったファイルを報告します。

  3. 3

    ビューを解釈する

    app/views/**/*.html.erb はリクエスト時にパースされ、構文木をたどるインタプリタ（tree-walking interpreter）で評価されます。開発環境ではエンジンが app/views/ をディスクから読み込み、テンプレートが変更されると再パースするので、ビューを編集しても再ビルドは不要です。cybertrain build はすべてのテンプレートをバイナリに埋め込みます（spin run gen -- --embed-views）。本番バイナリはそのテーブルからのみレンダリングし、各テンプレートのパースは一度だけです。Spinel には eval がないため、これは閉じた文法であり、本物の Ruby ではありません。

  4. 4

    グリーンスレッドで配信し、SQLite に保存する

    素の Ruby で書かれた HTTP/1.1 サーバーが、接続ごとに Spinel のグリーンスレッドを 1 本実行します。モデルは ffi_func/ffi_lib を通じ、4 接続のプール（WAL、busy_timeout、外部キー有効）で SQLite とやり取りします。SPINEL_WORKERS のデフォルトは 1 です。

  5. 5

    開発環境で再ビルドする

    cybertrain server は spin run gen を実行し、続いて spin run blog（blog はアプリ名）を実行します。開発環境ではバイナリが app/**/*.rb、config/**/*.rb、db/schema.rb、gen/**/*.rb を 0.5 秒ごとにポーリングします（ビューと gen/views.rb は除外）。変更があると spin run gen && spin build blog をバックグラウンドで実行し、成功すると再起動フラグ（外部からの kill -HUP が立てるのと同じフラグ）を立てます。するとサーバーは待ち受けをやめ、処理中のリクエストを捌き切ってから、新しいバイナリを同じポート・同じ PID で execv します。ビルドに失敗した場合は古いバイナリで配信を続け、コンパイラの出力をバナーとして表示します。cybertrain build が tmp/cybertrain-build.lock を保持している間は再ビルドをスキップします。これらはいずれも本番環境では読み込まれません。

05

Rails と CyberTrain

語彙は同じ。違うルールは明文化。

AOT コンパイラのために、いくつかの習慣が変わります。ここでは最初に出会うものを挙げます。

Rails と CyberTrain の違い（抜粋）
項目RailsCyberTrain
01コンソールrails consoleコンソールなし — Spinel には eval がない
02リロードコードを編集すると、実行中のアプリに反映されるRuby の変更には再ビルドが必要。開発環境では cybertrain server が代わりに行う（再ビルド、停止、execv）
03new アクションdef newdef new_action （new だと Klass.new(ctx) を覆い隠してしまう）
04コールバックbefore_action { do_thing }（暗黙の self）before_action { |c| c.do_thing } — 保存したブロックに対する instance_exec がないため、コールバックはコントローラー／レコードを明示的に受け取る
05ネストしたルーティングresources :posts do resources :comments endresources :posts do |posts| posts.resources :comments end — ネストしたブロックはマッパーを明示的に受け取る
06セッションセッションにはマーシャリングした任意のオブジェクトを保持できるセッションの値は String のみ、HMAC 署名付き cookie
07データベース多数のデータベースアダプターSQLite のみ、FFI 経由
08テストminitest / RSpecCybertrain::Test — リフレクションに基づくテストランナーは AOT では動かない

すべてを網羅してはいません。

06

始める前に

手元のマシンに必要なもの。

Ruby
3.2+ と RubyGems。cybertrain コマンドのためだけに必要です。アプリケーションが CRuby 上で動くことはありません。
Spinel
2026.09.12。他のバージョンでは未テストです。Spinel を必要とする最初のコマンドが ~/.cybertrain にビルドします（数分、初回のみ）。そのリリースの spinel がすでに PATH 上にあれば、それをそのまま使います。
ツールチェーン
cc と make（Spinel はすべてのプログラムを C にコンパイルします）、さらに Spinel のビルド用に git と curl。SQLite 3 のヘッダーとライブラリ：Debian/Ubuntu では libsqlite3-dev、macOS では Xcode コマンドラインツールに含まれています。OpenSSL のヘッダーは任意です。
ステータス
プレアルファ、バージョン 0.2.1、MIT ライセンス。サンプルのブログは Linux と macOS の CI で検証されています。

cybertrain doctor はこれらのツールとヘッダー、Spinel のインストールを確認し、足りないものがあればプラットフォームに応じたインストールコマンドを表示します。cybertrain setup は求めに応じて Spinel をインストールし、spin を自分で実行するための PATH の設定行を表示します。cybertrain spin ARGS... を使えば、その設定なしで実行できます。
